本文从单线程阻塞的问题出发，梳理传统解决方案以及 async/await 的基本工作方式。关于并发、并行与异步的概念边界，参见 concurrency。

异步的基本含义

异步是等待语义：发起操作后，不必阻塞当前控制流等待结果；结果就绪后再继续执行。

异步本身不等于并发或并行。单个任务也可以使用异步 API；多个异步任务能否并发推进，则取决于具体语言、运行时、调度器以及底层 I/O 机制。

单线程阻塞的困境

在最简单的执行模型中，一个线程一次处理一个任务。多个任务需要排队执行。

如果第 N 个任务在等待阻塞式 I/O（例如文件或网络操作），线程就会暂停，后续任务也只能等待，导致线程无法利用等待期间的 CPU 时间。

传统解决方案

多线程

为每个任务创建一个线程。这样可以让等待中的任务不阻塞其他任务，但线程会占用内存和操作系统资源，线程数量不能无限增长。

线程池

预先创建固定数量的线程，任务在线程池中排队执行。线程数量更可控，但当线程都在等待 I/O 时，任务仍然需要排队。

I/O 多路复用

由少量线程监听多个 I/O 操作，在某个操作就绪时再执行对应任务。相比为每个任务创建线程，这种方式能够用更少的线程处理大量 I/O。

回调带来的复杂度

如果一个任务包含多个 I/O 等待点，就需要在每个等待点拆分控制流，并把后续逻辑放进回调函数。这容易产生嵌套回调，使代码难以阅读、组合和维护。

async/await 的核心思想

async/await 试图保留同步代码的书写方式，同时让运行时在任务等待 I/O 时执行其他已就绪的任务：

  1. 使用少量线程，甚至单线程执行多个任务。
  2. 任务遇到可挂起的等待点时，保存当前执行状态并暂时让出执行权。
  3. 调度器执行其他已就绪的任务。
  4. 被等待的操作完成后，恢复原任务，从等待点之后继续执行。

这样可以避免手动拆分任务和编写层层嵌套的回调。但它是否真正并发、使用多少线程，以及等待操作是否可挂起，都取决于具体语言和运行时。

async 与 await

不同语言的语义并不完全相同，但通常可以这样理解：

  • async 表示一个函数具有异步执行语义，通常会返回一个任务、Promise 或 Future。
  • await 表示等待一个异步结果；等待期间，当前任务可以挂起，让运行时调度其他任务。
  • 结果完成后，函数从 await 之后继续执行，调用方不需要手动编写回调。

async/await 只是控制流抽象，不会自动创建线程，也不保证任务并行执行。异步任务的创建、取消、异常传播和资源释放仍然需要明确的生命周期管理。

async/await 的实现原理

状态机与协程

编译器或运行时通常会把包含 await 的函数转换为可暂停、可恢复的状态机。函数每次在等待点挂起时，都会保存恢复执行所需的局部状态；异步操作完成后，运行时根据保存的状态继续执行。

常见的相关机制包括：

  • generators
  • generator-based coroutines
  • native coroutines
  • yield from
  • await

执行模型

许多异步运行时采用协作式多任务（cooperative multitasking）：任务运行到可让出执行权的等待点时主动挂起，由调度器运行其他任务。

因此，异步函数内部如果执行了长时间的 CPU 密集型计算，或调用了阻塞式 API，就可能阻塞事件循环或占用执行线程，影响其他任务。

工程边界

使用异步模型时，需要额外关注：

  • 等待的操作是否真的支持异步挂起；
  • 是否混入阻塞式 I/O 或长时间 CPU 计算；
  • 任务由谁创建、等待、取消和回收；
  • 异常是否能传播到负责生命周期的调用方；
  • 运行时的调度器、事件循环和线程模型。
