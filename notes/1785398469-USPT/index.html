读论文：Twenty years of Bigtable

2026-07-302026-08-03
PAPER

Bigtable 如何在核心架构基本稳定的前提下，通过异步后台处理、计算存储分离和持续运维演化支撑二十年的规模增长。

https://dl.acm.org/doi/epdf/10.1145/3788853.3803095

  • 是什么（What）：
    • 一篇回顾 Bigtable 二十年演化的经验论文：哪些核心抽象从 2006 年保留至今，哪些内部机制被重构，以及复制、SQL、CDC、CRDT、物化视图等能力如何接入既有系统
  • 为什么（Why）：
    • 新系统论文很多，但长期运行并持续演化同一个超大规模数据库的公开经验很少；Bigtable 的价值在于展示架构稳定性、功能增长、资源效率和可运维性之间的真实取舍
  • 怎么做（How）：
    • 保持 tablet、SSTable、共享存储和单行事务等核心模型稳定，把复制、派生计算和完整性检查尽量移出前台写路径；再通过并行化、外部任务、分层扩缩容和专职 SRE 持续消除规模瓶颈

核心问题（问题演化）：

1. 核心架构如何跨越几个数量级的增长

2006 年的 Bigtable 面向 PB 级数据和数千台服务器。二十年后，论文披露的系统规模已经达到：

  • 管理约 10 EB 数据；
  • 峰值总负载约 70 亿 QPS；
  • 单表可超过 1600 万亿行、超过 1 EB；
  • 单集群峰值超过 2.5 亿 QPS；
  • Google 几乎所有产品领域、数千个内部团队都在使用。

规模增长了多个数量级，但核心架构变化不大：数据仍按有序 row key 划分为 tablets，由 tablet server 提供服务；持久数据仍以不可变 SSTable 组织在分布式文件系统中；客户端仍直接访问 tablet server，master 主要负责控制面。

论文真正要回答的不是“原始设计是否完美”，而是：哪些早期抽象为后续演化留下了接口，使系统无需反复重写核心读写路径？

2. 如何在不拖慢写入的情况下增加系统能力

二十年间，Bigtable 增加了跨地域复制、CDC、CRDT 聚合、SQL、物化视图和更强的数据完整性检查。如果每项功能都同步进入前台写路径，写延迟、可用性和故障模式会迅速恶化。

论文反复出现的答案是：把协调、派生计算和重型校验放到异步后台。前台路径只完成建立持久性和正确性所必需的最少工作，其余处理依靠日志、逻辑时钟、水位线、compaction 和可恢复后台任务推进。

异步并没有消灭复杂度，而是把复杂度从请求延迟转移到了：

  • 进度追踪与恢复；
  • 最终一致性语义；
  • 后台任务之间的交互；
  • 积压、优先级与资源隔离；
  • 用户可观察的 freshness。

3. 如何让有状态服务仍然容易迁移和扩缩容

Bigtable 不把 tablet 的持久数据绑定在 tablet server 本地磁盘，而是存储在 GFS 的后继者 Colossus 中。tablet server 只持有服务责任和缓存；迁移 tablet 时无需复制全部数据，只需把所有权交给另一台服务器。

这种计算与状态分离让 tablet 成为可调度单元，为以下能力奠定基础：

  • 故障恢复与负载均衡；
  • 快速扩缩容；
  • 外部 compaction；
  • batch worker 直接离线读取 SSTable；
  • Data Boost 等与在线服务隔离的分析能力。

代价也很明确：正常读取需要经过网络文件系统，对底层存储的可用性和尾延迟提出更高要求。Bigtable 选择承担稳定的远程访问成本，换取有状态计算节点的可移动性。

4. 如何在多个异步机制之间维护正确性

单个机制正确，不代表它与其他后台机制组合后仍然正确。论文中的复制与垃圾回收交互是典型例子：

  1. 三个副本 A、B、C 都有旧版本 v1；
  2. A 收到新版本 v2；
  3. B 在看到 v2 前按“只保留一个版本”的规则回收 v1；
  4. C 可能先从 B 收到删除 v1，再从 A 收到 v2；
  5. 两次复制之间，C 会暂时没有任何版本。

因此，按版本数量执行 GC 时，只有已经传播到所有副本的版本才能计入回收决策。局部状态不足以证明全局安全，后台系统同样需要跨机制不变量。

5. 谁来长期运行这样一个系统

Bigtable 最初设想由各用户团队自行部署维护，但实践证明大多数团队缺少运行它所需的专业知识。从 2006 年中开始，Bigtable 转为由专职 SRE 团队运营的公司级服务。

这说明“架构能否被少量专家稳定运营”与数据模型、存储格式一样，是系统可持续性的组成部分。一个只有作者才能安全操作的系统，很难跨越二十年。

设计思想（核心抽象）：

1. 稳定的数据模型：稀疏、多维、有序映射

Bigtable 延续了原始数据模型：

  • row key 决定数据排序、局部性和 tablet 划分；
  • column family 是 schema、权限和存储策略的基本单位；
  • timestamp 允许一个 cell 保存多个版本；
  • 单行读写和 read-modify-write 可以保持原子性。

这个模型比纯 key-value 丰富，又比关系模型更受约束。它牺牲跨行事务、join 和通用查询，换取可预测的分区、局部性和水平扩展。

2. Tablet 是存储、调度与负载均衡的共同边界

表按 row-key range 自动切分为 tablets。tablet server 服务一组 tablets，master 负责分配、故障检测和负载均衡，但客户端数据不经过 master。

这个边界有三个好处：

  1. 数据范围与服务责任可以独立迁移；
  2. 热点、拆分和均衡可以在局部处理；
  3. 控制面不位于每次数据访问的关键路径。

它也会暴露 row-key 设计的重要性。若大量请求集中到一个 key range，单个 tablet 仍可能成为热点。Bigtable 在迁移最热 tablet 时甚至会刻意保持其位置不变，转而迁走相邻冷 tablet，避免所有客户端缓存同时失效并引发 location lookup 风暴。

3. SSTable 与 LSM 结构提供可组合的后台演化点

近期写入先进入 commit log 和 memtable，随后转换为不可变 SSTable；读取合并 memtable 与多个 SSTable 的视图，compaction 在后台整理文件。

不可变文件降低并发读取与恢复复杂度，而 compaction 不只是存储维护任务，还逐渐成为承载新语义的位置。例如 CRDT counter 把已归并小计和未归并操作日志嵌入 LSM 层级，并在 merge compaction 中执行 trimming。删除操作也通过序列位置决定哪些历史增量不再有效。

这体现了一个重要的演化原则：新能力优先复用已有持久化与后台处理机制，而不是另造一条独立数据路径。

4. Pull-based 异步复制

目标副本主动从源副本拉取变更，而不是源副本向每个目标推送。每个目标独立记录进度，崩溃后从自己的水位线恢复。

这种设计：

  • 不要求副本在接收写入前互相协调；
  • 避免源副本追踪每个目标的投递状态；
  • 允许目标按自身速度消费；
  • 支持跨地域多主和高可用。

其语义是最终一致：一个副本接受写入后即可返回成功，不等待其他副本。复制默认使用低优先级和剩余资源，通常很快，但延迟不是固定承诺。系统还会周期性写入空操作，让没有用户写入的冷表也能持续推进 replication watermark，从而区分“已经追平”与“复制停滞”。

5. 把派生计算放到存储系统内部，但不放进前台写路径

Bigtable 从接近纯存储逐渐扩展到 SQL、CDC、CRDT 和物化视图：

  • SQL 与 row-key schema：把过去由应用约定的复合 row key 编码显式化，使 SQL 能识别各字段，并对具体片段执行范围扫描和谓词下推；
  • CDC：持续输出表上的变更，用于分析、同步和风控；
  • CRDT counter：让各副本独立处理可交换增量，并通过 changelog、compaction 和删除序列解决异步到达问题；
  • 物化视图：通过服务器端 mapper → shuffle table → reducer → finalizer 管道维护派生数据，每个阶段用 watermark 追踪进度。

它们的共同点不是功能形态，而是都能挂接到已有的日志、时钟、水位线和后台任务框架，无需改变前台写入协议。

6. 正确性也采用分层处理

Bigtable 对 row key、column key、value 以及文件使用 CRC 校验。客户端可以提供 CRC32C，否则由客户端库生成；校验贯穿 RPC 接收、commit log、memtable 和复制链路。

成本更高的检查放到后台：SSTable 构建完成、写入元数据前，系统会重新读取整个文件，解密、解压、逐项解析并再次验证 checksum。该过程由外部 file-builder job 执行，避免占用 tablet server 的前台服务能力。

7. 控制面保留中心协调，但把重活分散出去

master 仍是单进程控制面，但随着 tablet 数量增长，内部数据结构从粗粒度锁演进到细粒度锁；schema 更新由串行改为并行；原本由 master 串行执行的文件 GC，也改为由 tablet server 并行扫描元数据、写中间状态和删除文件，master 只负责切分工作与汇总结果。

同样的原则也用于外部 compaction、location cache proxy、offline access 和 bulk import：不需要持有核心状态、且能独立扩展的工作，应从有状态服务中移出。

8. 资源效率是数据库能力，而不只是财务指标

Bigtable 使用两层扩缩容：集群内部首先从 slack subpartition 的空闲服务器池快速增减机器；池容量不足或长期闲置时，再调用公司级资源池。前者响应快，并且能利用 tablet availability 等通用 autoscaler 看不到的领域信号。

缓存也有独立的 sizing 机制，根据总拥有成本动态寻找收益拐点，避免在命中率收益已经趋平后继续投入内存。在 10 EB 规模上，资源效率本身就是产品能力。

工程取舍（为什么这样设计）：

1. 共享存储换取状态可移动

  • 收益：故障恢复、负载均衡和扩缩容不必复制整个 tablet，计算节点更接近无状态；
  • 代价：正常读写依赖网络文件系统，远程访问与底层存储故障进入关键路径。

2. 异步处理换取低写延迟和高可用

  • 收益：复制和派生计算不阻塞前台写入，一个副本可独立接受请求；
  • 代价：用户必须理解最终一致、复制延迟、水位线和后台积压，系统还要处理多个异步机制的组合风险。

3. Pull replication 换取更简单的源端状态

  • 收益：每个目标管理自己的进度和恢复，源端不维护所有目标的投递游标；
  • 代价：目标之间可能以不同顺序看到更新，需要额外规则协调 GC、删除和 CRDT 语义。

4. 单行事务换取长期架构稳定

  • 收益：事务边界与 row key、tablet 的局部性一致，避免通用分布式事务进入写路径；
  • 代价：需要原子更新的数据必须放进同一行，可能形成超大行并带来性能问题。论文明确建议应用修改建模，而不是依赖 Bigtable 扩展事务语义。

5. 把计算纳入数据库换取更低运维复杂度

  • 收益：物化视图、CDC 和 SQL 不再要求用户维护独立 MapReduce、Dataflow 或其他计算系统，也减少跨系统一致性边界；
  • 代价：数据库承担更多资源调度、执行恢复和接口兼容责任，必须确保这些能力不会侵蚀核心 serving workload。

6. 大量 checksum 换取极低的静默损坏风险

  • 收益：数据在客户端、日志、内存、复制和文件多个阶段都能检测损坏；
  • 代价：CPU、I/O 和实现复杂度上升，完整 SSTable 回读尤其昂贵。Bigtable 接受这个成本，因为在其规模上任何可能的硬件或软件错误最终都会发生。

7. 稳定架构换取持续内部重构

“架构没有大改”不等于系统没有变化。锁粒度、schema 更新、文件 GC、compaction、location lookup 和批量访问路径都经历了并行化或外移。稳定的是职责与边界，不是二十年前的具体实现。

启发点（关键洞察）：

  1. 判断架构寿命，要看新功能挂在哪里：如果每个重要功能都必须改写核心读写协议，系统最终会被历史包袱压垮；Bigtable 的后台处理框架为新能力提供了稳定挂接点；
  2. 异步不是降低复杂度，而是重新分配复杂度：它用延迟和协调成本换取前台可用性，水位线、恢复、积压和机制交互必须成为一等设计对象；
  3. 计算存储分离首先解决的是状态可移动性：它不只是一种云架构标签，更直接决定恢复、均衡和扩缩容是否需要搬运大量数据；
  4. 后台任务同样需要组合正确性分析：复制和 GC 各自正确，组合后仍可能短暂丢失所有版本。评审后台机制时要检查它与 compaction、备份、删除和恢复的交互；
  5. 正确的核心抽象可以长期稳定，内部实现必须持续变化：tablet、SSTable 和单行事务延续了二十年，但锁、GC、缓存和调度不断重构；
  6. 简单架构会把复杂度转移给用户：单行事务让系统容易扩展，却迫使应用围绕 row key 重新建模。评价“简单”时必须说明复杂度最终由谁承担；
  7. 数据库了解通用基础设施看不到的领域信号：分层 autoscaling 不只依赖 CPU、内存，还使用 tablet availability；领域感知控制器可以比全局资源管理器更快、更准确；
  8. 真实工作负载会推翻设计者假设：Bloom filter 曾因要求查询同时指定 column family 和 column 而利用率不足；优化成熟系统时，先检查功能是否覆盖了用户真正采用的访问模式；
  9. 可运维性是架构属性：专职 SRE、metadata prober 和模拟正常用户的 blackbox latency prober，让系统行为可以被持续理解；
  10. 二十年系统最难复制的不是某个算法，而是演化能力：清晰边界、可恢复后台任务、资源隔离、监控和专业运营共同决定系统能否长期扩展。
