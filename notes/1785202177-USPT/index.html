当一个系统有很多状态、事件、条件分支时，如何用状态机把复杂行为显式化？

https://deniskyashif.com/2019/11/20/a-practical-guide-to-state-machines

  • 是什么（What）
    • 有限状态机把系统表示为有限的状态集合、输入事件以及状态转换函数；系统在任一时刻只处于一个状态，收到事件后按规则进入下一个状态
  • 为什么（Why）
    • 当业务规则散落在条件分支和布尔字段中时，很难确认哪些状态组合合法、哪些事件允许发生；状态机通过显式列举状态和转换，使遗漏、冲突与不可达状态可见
  • 怎么做（How）
    • 用枚举表示状态和事件，用模式匹配实现 State × Input → State；复杂工作流可拆成多个参与者的状态机，再通过乘积状态机分析系统整体行为和可达状态

核心观点：

状态机的价值不只是少写几个 if，而是把系统允许发生的行为变成一个可以枚举、组合和检查的模型。

状态机是一张有方向的行为图

有限状态机可以看成一张有向图：节点是状态，边是由输入事件触发的转换。一个确定性状态机至少包含：

  • 一组有限状态，例如门的 Open、Closed、Locked；
  • 一组输入事件，例如 open、close、lock、unlock；
  • 一个初始状态；
  • 一组可选的终止状态；
  • 一个转换函数，同一组“当前状态 + 输入”最多对应一个下一状态。

多个状态机可以组合成一个工作流

原文用在线商店、银行和顾客说明如何组合状态机：

  • 顾客可以支付或取消；
  • 商店收到支付后才能发货，并可以向银行兑付；
  • 银行需要保证一笔钱不能同时被取消和兑付，也不能重复退款或转账。

每个参与者先拥有自己的局部状态机。一个事件发生时，所有状态机同时观察它：相关参与者发生转换，不相关参与者通过自转换留在原状态。例如 cancel 对商店无关，那么商店在该事件下保持原状态。

可达性分析让隐含业务漏洞显形

乘积状态机列出了理论上的全部组合，但并非每个组合都能从初始状态到达。删除不可达状态后，剩余图就是系统真正可能经历的行为空间。

这个过程带来两种信息：

  1. 不可能状态：例如商店已经在转账后发货，银行却仍在等待兑付；模型让这种自相矛盾的组合不可达；
  2. 意外可达状态：原文在组合后发现 (2, c) 可以到达——货物已经发出，但顾客又成功取消了付款。这不是画图问题，而是原业务规则确实存在漏洞。

单独审查银行或商店的局部逻辑时，这个漏洞并不明显。只有把参与者组合起来，观察全局状态空间，跨组件的不变量才会显现。

状态机的适用边界

状态机适合以下问题：

  • 系统在任一时刻有清晰、有限且互斥的阶段；
  • 事件集合相对稳定，合法顺序是业务规则的重要组成部分；
  • 需要解释“当前为什么能或不能执行某个动作”；
  • 需要检查终态、不可达状态、死路或跨参与者的不变量。

它并不是所有领域的默认答案。若状态主要由大量连续数据决定，事件顺序高度开放，或人为流程经常绕过预定路径，强行枚举状态会造成状态爆炸。多个状态机的乘积规模等于各状态数量之积，参与者一多，完整状态空间会迅速增长。

因此，状态机应当用来显式表达真正重要的控制状态，而不是把每个字段组合都命名为一个新状态。

启发点（关键洞察）：

  1. 先识别状态，再写分支：如果多个布尔值共同决定行为，例如 isPaid、isCanceled、isShipped，应先检查它们是否其实在编码一个状态机；布尔值很容易表示出“既取消又兑付”这样的非法组合；
  2. 转换函数是业务规则的中心：把 State × Event → State 集中表达后，代码评审可以直接检查规则是否完整，而不必跨多个 handler 重建状态图；
  3. 未定义转换也属于设计：遇到无效事件时，是拒绝、忽略、保持原状态，还是记录告警，必须显式决定。默认分支不应悄悄吞掉模型缺口；
  4. 局部正确不等于全局正确：银行和商店各自的状态机都可能看起来合理，组合后仍会出现跨参与者漏洞。分布式工作流需要检查乘积状态中的全局不变量；
  5. 不可达状态是一种证明结果：它不只是可以从图上删掉的噪声，还说明某些非法组合无法由任何合法事件序列产生；
  6. 事件不等于命令发起者：状态机处理的是系统中发生的事件。同一个事件可以被多个参与者观察，各自转换或保持原状态；
  7. 状态与副作用需要分别推理：图可以证明允许的顺序，却不能自动保证数据库写入、网络调用、重试与状态更新的原子性；工程实现还需要幂等、事务或补偿机制；
  8. 警惕状态空间爆炸：组合状态机很强大，但状态数会相乘。应按清晰责任拆分局部机器，只在验证跨边界规则时构造必要的组合模型。
