HTTP/3 基于 QUIC 提供独立流、内建 TLS 与连接迁移，避免 TCP 层队头阻塞

  • S：HTTP/2 已能在一条连接上多路复用请求，但所有流仍共享同一个 TCP 字节流。
  • C：一个 TCP 包丢失时，TCP 必须先补齐有序字节流；即使其他 HTTP/2 流的数据已经到达，也不能交给应用。
  • Q：如何保留多路复用，同时避免不同请求在传输层互相阻塞？
  • A：HTTP/3 把 HTTP 映射到 QUIC。QUIC 在 UDP 之上实现可靠传输，每条流独立排序，并集成 TLS 1.3、连接迁移和更快的握手。

心智模型

HTTP/3 不是“把 HTTP 直接放到 UDP 上”。UDP 只提供数据报；可靠传输、拥塞控制、丢包恢复、流量控制和加密连接都由 QUIC 在用户态实现。

核心机制

独立的流

QUIC 连接可以承载多条双向或单向流。每条流内部仍然有序、可靠，但某条流丢包只阻塞该流，不会阻塞已经完整到达的其他流。这消除了 HTTP/2 在 TCP 层的跨流队头阻塞。

网络拥塞并没有消失：各流仍共享连接的拥塞控制和网络容量。HTTP/3 解决的是“丢包后所有流必须等待同一 TCP 序列”的问题，而不是让丢包变得无成本。

TLS 1.3 与握手

QUIC 把 TLS 1.3 握手集成进传输握手：

  • 首次连接通常以 1-RTT 建立加密会话，不再串行执行 TCP 握手和 TLS 握手。
  • 恢复已有会话时可使用 0-RTT 提前发送应用数据。
  • 0-RTT 数据可能被重放，只适合幂等或具备防重放机制的操作，不能无条件用于有副作用的请求。

QUIC 除少量必要头部外默认加密传输元数据，协议演进也不容易被中间设备固化的 TCP 识别逻辑阻碍。

Connection ID 与连接迁移

TCP 连接由源/目的 IP 和端口识别，设备从 Wi-Fi 切换到蜂窝网络后通常需要重连。QUIC 使用 Connection ID 标识逻辑连接，因此地址变化后可以验证新路径并延续连接。迁移不是无缝魔法：新路径仍需验证，拥塞控制状态也需要谨慎处理。

QPACK

HTTP/2 使用 HPACK 压缩头部，但其动态表更新依赖有序 TCP 流。HTTP/3 使用 QPACK，把编码器/解码器指令放在专用单向流中，并允许请求流引用动态表。它在压缩率和阻塞风险之间权衡；引用尚未到达的表项时，请求流仍可能等待，但不会把整条连接拖住。

与 HTTP/2 对比

维度 HTTP/2 HTTP/3
传输 TCP QUIC over UDP
加密 通常使用 TLS，协议上可分离 QUIC 强制集成 TLS 1.3
多路复用 HTTP 层多流，TCP 层单一有序字节流 QUIC 原生多流、流间独立交付
丢包影响 可能阻塞连接内所有流 通常只阻塞发生丢包的流
地址变化 通常需要重连 可通过 Connection ID 迁移
头部压缩 HPACK QPACK

部署边界

  • 客户端通常先通过 Alt-Svc 或 HTTPS DNS 记录获知 HTTP/3 端点；QUIC 不可达时应回退到 HTTP/2 或 HTTP/1.1。
  • 部分网络会限制 UDP，NAT、负载均衡器和可观测工具也需要理解 QUIC。
  • QUIC 在用户态更易演进，但加密使传统中间设备难以检查内部状态，排障方式会变化。
  • 是否更快取决于 RTT、丢包率、连接复用和实现质量；稳定低延迟网络中的收益可能不明显。
