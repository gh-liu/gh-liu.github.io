通过分片、SQL Router 与负载均衡，把数百个数据库节点抽象成一个逻辑数据库。

https://planetscale.com/blog/making-768-servers-look-like-1

  • 是什么（What）
    • 一种分片数据库架构：将数据和查询分散到多个独立主库，再由理解数据拓扑与 SQL 的 Router 对应用隐藏物理分布
  • 为什么（Why）
    • 单机纵向扩容与只读副本无法突破单主库的写入、存储容量和大库备份瓶颈；分片能并行扩展容量与读写吞吐，但会把复杂度转移到数据库中间层
  • 怎么做（How）
    • 选择分片键和映射策略，用拓扑元数据描述数据分布；Router 解析并规划 SQL，将请求路由到单个或多个分片并合并结果；再用多个 Router 和可选的 NLB 消除 Router 单点与吞吐瓶颈

核心观点：

“让 768 台服务器看起来像 1 台”的关键不是消除分布式复杂度，而是建立一个逻辑数据库抽象：应用只面对统一的连接入口和 SQL 接口，Router 则负责承接数据定位、查询分发与结果聚合。

为什么只做单机扩容和只读副本还不够

  1. 写吞吐仍受单个 Primary 限制：
  • 常规主从复制只允许 Primary 处理 INSERT、UPDATE、DELETE
  • 提交写入前需要记录 WAL 并刷入持久化存储，Primary 上所有连接仍会竞争共享的写入路径
  • 增加 Replica 只能分担读请求，不能分担 Primary 的写入压力
  1. Replica 不增加有效数据容量：
  • 每个 Replica 都保存 Primary 的完整数据和索引
  • 增加副本提高的是读吞吐、可用性和数据耐久性，而不是单个逻辑数据库能够容纳的数据量
  1. 单体大库的备份窗口过长：
  • 数据库到对象存储的带宽有限，数 TB 乃至更大的数据库备份可能需要数小时或数天
  • 备份和恢复耗时会直接影响 RPO、RTO，也让备份校验和故障演练变得昂贵
  1. 纵向扩容存在收益递减：
  • 增加 CPU、内存和 I/O 能力是简单且有效的早期方案
  • 但共享资源竞争和协调开销会使扩展低于线性增长；机器越大，并不意味着数据库吞吐能同比增长

分片如何突破这些限制

分片将一个逻辑数据库拆成多个拥有独立 Primary 的物理数据库。每个分片只保存部分数据，也只承担部分查询和写入：

方案 数据分布 读扩展 写扩展 容量扩展 主要代价
纵向扩容 单份 有限 有限 有限 成本上升、存在硬件上限
只读副本 每个节点保存全量副本 是 否 否 复制延迟、Primary 仍是瓶颈
分片 每个分片保存部分数据 是 是 是 路由、跨片操作和运维复杂度

文章用两个规模说明这种拆分：

  • 2 TB 数据可以拆为 4 个分片，每片约 500 GB，理想情况下各承担约四分之一流量
  • 1 PB 数据可以拆为 256 个分片，每片约 4 TB；若每片配置 1 个 Primary 和 2 个 Replica，共需要 256 × 3 = 768 台服务器

这里的关键变化是：Replica 在分片内部提供高可用与读扩展，Shard 在分片之间提供写吞吐与数据容量扩展，两者解决的问题不同，可以组合使用。

Router 是逻辑数据库抽象的核心

普通 Postgres Proxy（如 PgBouncer）主要负责连接池化、连接复用、排队和故障切换期间的缓冲；分片 Router 除此之外，还必须理解 SQL 和数据拓扑：

  1. 写入路由：根据表的分片键计算目标分片，将数据写入对应的 Primary
  2. 单分片查询：从谓词中提取分片键，直接把 SQL 发送到唯一目标分片
  3. 跨分片查询：找出所有可能包含结果的分片，并行下发查询，在 Router 中聚合结果后返回应用
  4. 连接管理：复用到各个分片的数据库连接，并在突发流量或故障恢复时排队请求

例如按 user.id 的哈希值分片：

  • SELECT email FROM user WHERE id = 4 能由 id = 4 唯一定位到一个分片
  • SELECT email FROM user WHERE id BETWEEN 3 AND 5 可能覆盖多个分片，Router 需要生成分布式执行计划、向相关分片发起查询，再合并结果

第二类查询意味着 Router 不能只是按字符串转发 SQL，而要具备完整的 SQL Parser、Planner 和结果聚合能力。若查询还包含 ORDER BY、LIMIT、聚合或跨表 JOIN，合并过程会更复杂，也更消耗 Router 的 CPU、内存与网络资源。

多个 Router 如何仍表现为一个入口

一个 Router 无法承载数百万 QPS，也会成为单点，因此实际系统需要横向部署多个 Router。应用可以通过 Network Load Balancer（NLB）访问统一域名：

一次完整连接过程是：

  1. 应用使用统一连接地址，例如 mydb.pscale.com
  2. DNS 将域名解析到 NLB 地址
  3. NLB 为新连接选择一个 Router，并在连接生命周期内维持该映射
  4. 应用发送 SQL，流量沿 App → NLB → Router → Shard 传递
  5. Router 隐藏物理分片和结果合并过程，应用继续把它当作一个逻辑数据库

NLB 不是必需的。让客户端直接感知多个 Router 可以减少一次网络跳转和少量延迟，但会把服务发现、负载分配和故障处理复杂度重新暴露给应用。

“看起来像一个数据库”的边界

统一连接串只隐藏了拓扑与路由复杂度，并不自动恢复单机数据库的全部语义和成本模型：

  • 跨片事务：原子提交需要分布式事务协议，否则只能限制事务范围或接受补偿语义
  • 跨片 JOIN 与聚合：可能产生 Scatter-Gather、大量中间数据和尾延迟，性能通常不再等价于单机执行
  • 全局约束：跨分片的唯一索引、外键、全局序列和一致性校验更难实现
  • 热点分片：哈希分片能均匀分布随机键，却不能保证业务访问均匀；超级用户或热点租户仍可能压垮单片
  • 重分片：增加分片数需要在线迁移数据、双写或流量切换，并保持迁移过程的一致性
  • 故障与拓扑变更：Router 必须及时获知主从切换和分片变化；多个 Router 之间还要避免使用不一致的旧拓扑
  • 备份与恢复：分片缩短单节点备份窗口，但要获得全库一致快照，仍需协调 256 个分片的时间点和恢复顺序
  • 可观测性：逻辑上的一次 SQL 可能展开成数百个物理请求，需要跨 Router 和 Shard 追踪延迟、错误与资源消耗

原文聚焦的是统一访问层，没有展开上述问题。Neki/Vitess 的价值不仅是一个 Proxy，而是围绕路由、拓扑、故障处理和运维提供完整的分片系统。

启发点（关键洞察）：

  1. 抽象不会消除复杂度，只会重新安置复杂度：应用获得了简单的连接模型，但 Router 和数据库平台必须接管 SQL 解析、执行计划、连接池、拓扑管理、故障恢复与结果合并。平台能力越强，业务侧越简单。
  2. 先按瓶颈类型选择扩展方式：只读副本针对读吞吐和可用性，分片针对写吞吐与容量。若瓶颈只是慢 SQL、索引或连接数，直接分片往往是在用最高复杂度方案解决更低层问题。
  3. 分片键决定系统的性能上限：好的分片键既要让数据和流量均匀分布，又要让大多数事务与查询能被限制在单片内。设计时应优先围绕访问局部性，而不是只追求数学上的数据均匀。
  4. 最便宜的分布式查询，是不跨分片的查询：Router 可以支持 Scatter-Gather，不代表业务应依赖它。表的共置、租户键贯穿和查询模式约束，往往比增强跨片执行器更有效。
  5. 控制面与数据面必须分离理解：SQL Router 位于数据面，负责高频查询转发；分片规则、拓扑变更、主从切换和重分片属于控制面。768 台服务器能否稳定表现为一个数据库，更取决于两者能否一致协作。
  6. “单一入口”是可演进性的基础：应用依赖逻辑连接地址而不是物理节点，使底层增加 Router、替换 Primary 或迁移分片时不必修改所有业务服务。这与负载均衡器、服务发现和虚拟存储卷的设计思想一致。
  7. 分片降低的是每个故障域的规模，不是系统总复杂度：单片备份、恢复和故障切换会更快，但分片数量增多后，故障发生频率、协调工作和观测维度都会增加。
  8. “几 TB 后就应该分片”不是普适阈值：这是原文基于 PlanetScale 产品经验给出的建议，实际决策应由数据增长率、写入吞吐、备份窗口、访问模式、团队运维能力和成本共同驱动，而不能只看数据库大小。

行动：

  1. 评估数据库扩展时，分别测量 CPU、IOPS、WAL 写入、数据容量、备份/恢复窗口和读写比例，先确认真正瓶颈。
  2. 在引入分片前统计 Top SQL，验证绝大多数读写能否携带候选分片键并在单片完成。
  3. 用“数据均匀度、访问均匀度、事务局部性、重分片成本”四个维度评审分片键，而不是只检查哈希是否均匀。
  4. 明确系统对跨片事务、JOIN、唯一约束、全局排序和分页的语义及性能边界，不把 Router 的透明性当作无限能力。
  5. 容量规划时同时预算数据库节点和 Router 层；对 Scatter-Gather 查询重点监控扇出数、P99 延迟、中间结果大小和失败比例。
  6. 把重分片、单片故障、Router 故障、拓扑配置不一致和全库恢复纳入上线前演练，验证抽象在故障时仍然成立。
