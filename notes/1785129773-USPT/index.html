从架构演进、分布式基础能力到云原生基础设施，建立构建可靠大型系统的完整知识地图。

https://book.douban.com/subject/35492898

在线开源版本：https://icyfenix.cn

  • 是什么（What）：
    • 周志明围绕“如何构建可靠的大型分布式系统”整理的一张架构知识地图，从架构演进讲到远程调用、事务、流量、安全、共识、可观测性、容器、服务网格与技术决策方法
  • 为什么（Why）：
    • 分布式把单机内部可靠、快速、确定的调用变成跨网络协作，获得独立扩展和故障隔离能力的同时，也引入延迟、部分失败、一致性和运维复杂度；架构设计必须理解每项技术在解决什么问题、又制造了什么问题
  • 怎么做（How）：
    • 先从业务目标和系统约束出发选择架构风格，再分别设计通信、事务、流量、安全与观测能力；优先复用成熟基础设施，但始终保留对其语义、失败模式和适用边界的理解

核心观点：

架构不是技术组件的集合，而是在具体约束下分配复杂度：决定哪些问题由业务代码解决，哪些下沉到框架、平台和基础设施，以及这些选择要付出什么代价。

架构风格是连续演进，不是等级排名

书中从原始分布式、单体、SOA、微服务、后微服务到 Serverless 回顾服务架构演进。每种架构都由当时的主要矛盾推动：

  • 单体把调用和事务收拢在一个进程内，开发、部署和调试简单，但模块边界容易随规模增长而腐化；
  • SOA尝试通过企业级服务与集中治理复用能力，却可能形成重量级中间件和中心化瓶颈；
  • 微服务用独立部署、技术异构和团队自治换取演化能力，同时把通信、事务、观测和运维问题暴露出来；
  • 后微服务/云原生将容错、路由、安全和观测等非功能能力下沉到 Kubernetes、sidecar 和 service mesh，让业务进程重新聚焦功能；
  • Serverless进一步把运行时资源和伸缩交给平台，但会增加平台约束、冷启动、状态管理和可移植性问题。

后出现的架构并不天然优于先前架构。架构选择取决于业务规模、团队边界、发布频率、可靠性要求与基础设施成熟度。能用模块化单体解决的问题，不应为了“先进”而过早分布式。

远程调用永远不是本地调用

本地调用通常快速、可靠，并且只有成功或失败两种清晰结果；远程调用要面对网络延迟、超时、丢包、重复、乱序和对端部分失败。一次超时只说明调用方没有按时收到响应，并不能证明服务端没有执行。

因此，分布式接口必须显式设计：

  • 超时与 deadline 如何传播；
  • 哪些操作可以安全重试；
  • 如何通过幂等键或去重避免重复副作用；
  • 错误属于业务拒绝、暂时不可用还是未知结果；
  • 序列化协议和接口如何兼容演进。

RPC 框架可以隐藏编码、连接和寻址细节，但不能抹掉网络语义。所谓“透明远程调用”如果让开发者忘记这些差异，反而会制造更隐蔽的故障。

分布式事务是在一致性、可用性和成本之间选择

本地事务依赖日志、锁、MVCC 等机制实现 ACID。一旦数据跨越节点和服务，原子提交需要额外协调：

  • 2PC 等全局事务追求强一致，但协调者、锁持有时间和故障恢复会影响可用性与吞吐；
  • 可靠事件队列把事务拆为本地提交与异步消息，获得最终一致，但需要幂等消费和补偿；
  • TCC 将业务显式拆成 Try、Confirm、Cancel，控制力强，但侵入业务且悬挂、空回滚等边界复杂；
  • Saga 把长事务拆成一系列本地事务及补偿动作，适合长流程，但补偿不等于数据库回滚，业务必须接受中间状态。

不存在脱离业务语义的万能方案。先判断真正需要原子的业务不变量，再选择一致性范围；不要因为技术上能够构造全局事务，就默认所有步骤必须同步强一致。

流量系统是一条多级分流链路

请求从用户到服务端，会依次经过浏览器/客户端缓存、DNS、传输链路、CDN、负载均衡和服务端缓存。性能优化不是只在数据库前放一个缓存，而是把请求尽可能拦截在成本最低、距离用户最近的位置。

每一级分流都有一致性代价：缓存失效、陈旧数据、穿透、击穿、雪崩和热点迁移都来自“副本比源数据更快，但不再是唯一真相”。设计缓存时必须同时说明命中路径、回源路径、失效策略和故障降级。

分布式可靠性来自一组共同基础能力

当服务数量增加后，许多问题不应由每个业务团队重复实现：

  • 共识与协调：Paxos、Raft、Gossip 等解决不同范围的一致认知和状态传播；
  • 服务发现与路由：维护逻辑服务到实例的动态映射；
  • 负载均衡：在容量、延迟、亲和性和故障之间分配请求；
  • 容错：通过超时、重试、熔断、隔离、降级控制故障传播；
  • 流量控制：通过限流和背压让系统在过载时保持可预测；
  • 安全：认证“你是谁”、授权“你能做什么”，并管理凭证、加密、传输与输入验证；
  • 可观测性：通过日志、追踪和度量，从外部输出推断系统内部状态。

这些能力可以存在于类库、框架、代理或平台。位置不同，意味着所有权和复杂度分配不同：类库容易定制但会侵入应用并产生语言异构；sidecar 与 service mesh 更统一，却增加平台本身的学习、资源和排障成本。

不可变基础设施让部署结果更可重复

容器镜像把程序及其依赖封装为不可变制品，实例发生变化时倾向于替换而不是登录机器原地修改。Kubernetes 在此基础上提供声明式编排、调度、自愈和扩缩容；service mesh 再将服务间通信治理放入数据平面与控制平面。

不可变并不意味着系统没有状态，而是将状态从随意修改的计算实例中剥离，交给有明确持久化和复制语义的存储系统。这样才能让计算节点安全地创建、销毁和迁移。

技术决策要回答目的、前提、边界和治理

引入微服务或云原生能力时，应依次回答：

  1. 目的：当前矛盾是什么，为什么现有架构不能满足？
  2. 前提：团队、自动化、测试、监控和交付能力是否足以承担新架构？
  3. 边界：服务按什么业务能力拆分，事务和数据所有权在哪里终止？
  4. 治理：服务增加后，如何控制依赖、版本、流量、故障和认知复杂度？

技术选择只有放进这个上下文才有意义。脱离约束比较“微服务还是单体”“REST 还是 RPC”，通常得不到可执行结论。

启发点（关键洞察）：

  1. 分布式首先是一种成本模型变化：进程内调用变成网络请求后，延迟、失败和一致性语义都改变了；拆服务前应确认收益足以覆盖这些成本；
  2. 不要把基础设施透明性误解为问题消失：框架和 service mesh 可以统一实现重试、熔断和认证，但业务仍要理解重复执行、降级结果和安全边界；
  3. 先定义不变量，再选择事务方案：真正需要保护的是库存不能为负、资金不能凭空产生等业务事实，而不是抽象地追求所有流程 ACID；
  4. 缓存、复制和异步化本质上都在制造多份状态：性能与可用性的提升，通常以同步和一致性复杂度为代价；
  5. 可观测性不是上线后的附加功能：分布式系统无法靠单步调试还原全局行为，日志、追踪、指标及上下文传播必须在设计阶段进入协议；
  6. 架构复杂度不会消失，只会移动：从应用移到平台能减少业务团队重复劳动，但平台团队必须承担统一治理、兼容和故障排查责任；
  7. 自动恢复必须建立在状态外置与声明式目标之上：如果实例保存不可替代的本地状态，编排系统就无法安全地销毁并重建它；
  8. 架构演进应由瓶颈驱动：先明确当前限制，再引入解决该限制的最小能力；不要用未来可能出现的问题为今天预付全部复杂度；
  9. 组织边界会进入系统边界：微服务自治只有在团队同时拥有代码、数据、发布和运行责任时才成立；只拆代码不拆责任，通常只会增加协调；
  10. 可靠性来自受控失败，而不是假设不会失败：超时、隔离、背压、降级和恢复的目标，是让故障范围、持续时间和后果保持可预测。

行动：

  1. 为现有系统画出一次请求经过的客户端、DNS、网关、服务、缓存、消息和存储链路，并标出每一步的超时、重试与所有者；
  2. 选择一个跨服务流程，写清它真正维护的业务不变量、允许出现的中间状态以及失败后的恢复方式；
  3. 检查重试配置：只有具备幂等语义或可靠去重机制的操作才能安全地自动重试，并确认超时后未知结果不会产生重复副作用；
  4. 用日志、追踪和指标分别回答“发生了什么”“请求经过哪里”“系统整体是否异常”，补齐无法回答的观测盲区；
  5. 每次引入新基础设施前记录目的、前提、边界和退出方案，在评审中同时说明收益与新增故障模式。

金句：

  1. 架构并不是被“发明”出来的，而是持续进化的结果。
  2. 远程调用不会因为形式上像本地调用，就获得本地调用的可靠性与性能。
  3. 架构设计的重点不是消灭复杂度，而是让复杂度出现在最合适的位置，并由最合适的人承担。
  4. 可观测性是可以由系统的外部输出推断其内部状态的程度。
  5. 没有一种架构天然先进，只有它是否适合当前问题、团队和约束。
