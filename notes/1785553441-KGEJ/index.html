以 Bucket、Key、Object 为核心抽象，理解 S3、R2 等对象存储

  • S：图片、视频、备份、日志、数据湖等海量非结构化数据，需要低成本、长期可靠地保存。
  • C：本地文件系统容量受单机限制；分布式文件系统运维复杂；数据库不适合存放大对象。
  • Q：如何提供容量近乎无限、可靠且可通过网络访问的存储？
  • A：对象存储将数据抽象成独立对象，以 Bucket + Key 定位，通过 HTTP API 整体读写，由服务端负责分片、副本、校验与扩容。

对象存储 = 扁平 Key 空间 + 整体对象读写 + 托管的持久性与扩展性

心智模型

对象存储不是远程磁盘，也不是传统文件系统，而是一个超大规模的 key -> bytes + metadata 映射。

  • Bucket：对象的容器，也是区域、权限、版本、生命周期等策略的边界。
  • Key：Bucket 内对象的唯一名称。
  • Object：数据本体、元数据和可选版本 ID。
  • Prefix：Key 的前缀；logs/2026/08/a.json 看似有目录，实际只是一个字符串 Key。

读写模型

  • PUT：上传或整体覆盖对象，不能像磁盘一样原地修改几个字节。
  • GET：读取整个对象，也可用 Range 只读取指定字节范围。
  • HEAD：只读取大小、类型、ETag 等元数据。
  • LIST：按 Prefix 分页列举对象。
  • DELETE：删除对象；开启版本控制后通常只是产生删除标记。
  • 大对象使用 Multipart Upload 并行上传；失败时只需重传分片。

一致性由具体产品定义；现代主流服务通常提供强一致性。多个客户端同时覆盖同一个 Key 时，仍需要用版本号或条件请求处理并发冲突。

为什么适合海量数据

  • 容量与扩展：无需预分配磁盘，服务端自动扩展。
  • 持久性：数据跨多个设备保存并持续校验、修复；持久性不等于服务永远可用。
  • 成本分层：可按访问频率选择热、冷、归档存储，并用生命周期规则自动迁移或删除。
  • 计算分离：多个计算节点可以共享同一份数据，适合静态资源、备份、日志和数据湖。

不适合的场景

  • 低延迟、高频、细粒度随机读写。
  • 依赖文件锁、原子重命名、追加写等 POSIX 文件系统语义。
  • 大量小文件且每个文件都被频繁访问。
  • 需要复杂查询、事务或记录级更新的数据。

对象重命名通常需要 Copy + Delete；追加或局部修改通常需要生成新对象。因此，设计时应优先采用不可变对象、批量写入和新 Key 发布。

常见场景

  • 静态资源与 CDN 源站
  • 数据库备份、归档与灾难恢复
  • 日志、埋点与数据湖
  • 图片、音视频和用户上传文件
  • 构建产物、模型与软件包分发

性能与成本

一次请求通常包含网络和服务端处理开销，延迟远高于内存或本地磁盘。每个请求还可能单独计费，因此应避免大量细粒度读写。

  • 合并小对象，减少请求数量。
  • 大对象使用分片并行上传，下载时可并发 Range GET。
  • 高频读取配合 CDN 或缓存，避免反复跨网络访问源站。
  • 成本不仅是存储容量，还包括请求次数、数据传出、检索和提前删除费用。

可靠性与安全

  • 如果服务支持，开启 Versioning，降低误删和覆盖风险；它不能代替独立备份。
  • 使用 Lifecycle 清理旧版本、未完成的分片上传，并迁移冷数据。
  • 默认保持私有，通过访问策略或临时凭证授权。
  • 客户端直传/下载可使用有过期时间的 Presigned URL，无需暴露云凭证。
  • 需要跨地域容灾时配置复制；具体持久性和可用性范围由产品与存储类型决定。

S3 与 R2

S3 是 AWS 的对象存储产品，其 API 已成为事实标准；Cloudflare R2 提供 S3 兼容 API。因此，二者的核心模型和常见操作基本相同：

  • Bucket / Key / Object
  • PUT / GET / HEAD / DELETE / LIST
  • Multipart Upload、Range GET、Presigned URL
  • 常见 S3 SDK 和工具

但 S3 兼容不等于能力完全相同。身份与权限、存储类型、版本控制、生命周期、复制、事件通知、校验算法、请求限制和计费模型都可能不同；迁移时应核对目标服务的兼容性文档，而不是只替换 endpoint。

深入 S3

以 S3 为例再看两个进阶主题：一致性语义，以及构建在 S3 之上的系统架构。

强一致性与条件写

  • 2020 年以后，S3 的 GET、PUT 和 LIST 都具备强一致性：Amazon S3 Update: Strong Read-After-Write Consistency
  • Conditional write 提供单对象 CAS：Amazon S3 functionality for conditional writes

S3-native 系统架构

S3-native 系统的核心不是直接从 S3 查，而是把 S3 当作不可变对象层，在其上补齐元数据、缓存与合并等能力。
