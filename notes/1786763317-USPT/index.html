EOPL 阅读地图：通过逐步实现解释器理解作用域、类型、控制流、状态与模块

本篇是第三版阅读地图。学习载体是 Scheme/Racket 风格的解释器，目标不是学语法，而是学会给语言特性定义可执行语义。

  • 是什么（What）：一本以“定义数据类型 → 写解释器 → 扩展语言”为方法的编程语言教材，逐步引入作用域、过程、状态、数据抽象、控制流、类型和模块。
  • 为什么（Why）：只会使用语言特性，容易把闭包、对象、continuation 或类型检查当成黑盒；实现解释器会迫使我们明确语法、运行时表示和求值规则。
  • 怎么做（How）：每次只增加一个语言特性，先写语法和语义，再修改解释器并用小程序验证；保持不同阶段的解释器可运行，不在同一份代码上无限打补丁。

心智模型

解释器的参数揭示语言的隐含机制：

  • expression：当前要求值的程序结构；
  • environment：名字到绑定的映射；
  • store：位置到可变值的映射；
  • continuation：当前计算完成后“接下来做什么”；
  • type environment：名字到类型信息的映射。

每引入一个新参数，都是把原先藏在宿主语言调用栈或可变状态中的机制显式化。

阅读主线

1. 数据定义与递归程序

先用归纳数据定义描述列表、树和抽象语法，再让程序结构跟随数据结构：一种数据变体对应一个分支，递归字段对应递归调用。这是后续解释器可维护性的基础。

关键习惯：

  1. 写出数据定义和合法示例；
  2. 为每个变体列出处理分支；
  3. 明确递归调用处理的是哪个更小子结构；
  4. 用构造器和观察器隔离具体表示。

2. 词法作用域、环境与闭包

环境不是“所有变量值的表”，而是一串具有遮蔽关系的绑定。求值变量时查询最近绑定；进入 let 或调用过程时扩展环境。

3. 递归与过程表示

letrec 的难点是过程闭包需要引用尚在构造中的递归环境。可以用递归环境数据结构、占位位置或延迟绑定表达这种自引用。重点不是某个技巧，而是保证“过程体中的递归名字解析到同一组过程”。

不同过程表示还揭示表示独立性：调用方只依赖 apply 接口，不应知道过程是 AST + 环境，还是宿主语言函数。

环境负责词法绑定，store 负责随时间变化的内容。把两者混在一起会难以解释别名：两个变量可以指向同一 location，因此修改一方能被另一方观察到。

Store 可以是全局可变结构，也可以作为参数和返回值显式传递。后者更啰嗦，却使副作用的顺序进入函数签名，便于推理。

5. 数据抽象与对象

对象的一种闭包编码是携带字段环境的过程值；EOPL 的类/对象解释器则显式表示对象、字段引用和方法环境。两种表示都说明：消息发送可以拆成方法查找与调用，类、继承、self 和 super 可由环境扩展、方法表和绑定规则组合出来，而不必先假设为 VM 原语。

这一实现视角有助于区分：

  • 对象身份与字段内容；
  • 方法定义环境与接收者环境；
  • 继承中的代码复用与子类型关系。

6. Continuation 与控制流

Continuation 表示剩余计算。把宿主语言调用栈中的控制状态改写成显式数据类型后，解释器从 direct style 变为 continuation-passing style（CPS）。

条件、函数实参求值和异常处理都对应不同 continuation 变体。显式 continuation 让求值顺序、异常跳转、协作式线程等机制可以检查和改写，而不再依赖宿主栈的隐式行为。

7. 类型检查与类型推断

解释执行回答“程序运行会得到什么”；类型检查回答“程序运行前能排除哪些错误”。类型环境保存变量类型，检查器按表达式结构生成或验证约束。

需要区分：

  • 类型安全不等于程序逻辑正确；
  • 静态类型是对运行时行为的保守近似；
  • 类型推断省略的是标注，不是类型规则；
  • 多态、子类型和可变状态组合后会引入额外约束。

可与 type system 和 The Little Typer 对照。

8. 模块

模块为一组定义提供边界，接口暴露可见名称与类型。检查模块时，应分别处理实现环境和对外接口，验证实现满足声明后，只把接口加入调用方环境。

模块系统的核心价值不是文件拆分，而是隐藏表示、控制依赖和支持独立推理。

核心观点

理解一个语言特性，就是能说清它的语法、运行时表示、求值规则，以及它与已有特性组合时必须保持的不变量。

  1. 解释器是可执行规格：语义歧义最终会表现为无法决定如何求值。
  2. 表示是设计决策：环境、闭包、store 和 continuation 的表示会决定哪些扩展容易，哪些操作昂贵。
  3. 显式化带来控制力：把栈、状态或类型约束变成数据后，才能观察、验证和转换它们。
  4. 语言特性会交互：状态影响闭包和类型，多线程影响 continuation 与 store；分别理解不等于组合后仍正确。
  5. 小步扩展优于一次造完整语言：每个解释器阶段都提供一个可验证的语义增量。

实践计划

  • 用 Racket 或熟悉的函数式语言完成一个最小 LET 解释器。
  • 每新增特性，先写一组合法程序和一组应失败程序。
  • 为 environment、store、closure、continuation 分别画出运行时数据结构。
  • 保留 direct style、CPS 和寄存器化解释器，比较它们的控制状态位于何处。
  • 给解释器增加一个小特性，例如 break、异常或惰性求值，并写清与现有语义的组合规则。
  • 将最终实现与 Interpreter 的编译器流水线视角对照。

阅读边界

  • 示例语言刻意保持很小，不能直接代表生产语言实现。
  • 教材重心是语义和解释器变换，不是 parser 工程、优化器、GC 或机器码生成。
  • Scheme 风格代码要求适应递归和代数数据类型式思考；若直接翻译为大量可变类，容易掩盖书中的结构。
