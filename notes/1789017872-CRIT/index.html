读博客：Make Invalid States Unrepresentable

2026-09-102026-09-10
BLN

通过数据结构、关系与约束缩小状态空间，让非法状态无法表示，而不是在每个写入口反复补救。

https://kevinmahoney.co.uk/articles/applying-misu

  • 是什么（What）
    • 让非法状态无法表示（Make Invalid States Unrepresentable，简称 MISU）是一种建模原则：减少系统能够处于的状态，尤其把不满足业务不变量的状态从表示空间中排除。
  • 为什么（Why）
    • 如果模型允许 gap、overlap、缺失终点等组合，校验只能在每个写入口重复补救，API 之间仍可能互相制造矛盾。更精确的表示把约束交给结构本身，使正确状态成为默认状态。
  • 怎么做（How）
    • 先写清楚不变量，再选择能直接表达它的数据结构；删除可由其他事实推导出的冗余数据；把内部模型与外部兼容形状解耦，必要时用投影（如 database view）提供旧接口。

不要问：如何检测非法状态？ 先问：为什么我的模型允许这个非法状态存在？

最好的 invariant，不是被代码检查出来的 invariant，而是由数据模型自动成立的 invariant。

核心观点

设计的重点不是为所有错误状态增加检查，而是缩小状态空间，让错误状态根本没有自然的表示方式。

这不是把所有规则都硬编码进类型的口号，而是寻找更少冗余、更贴近领域事实的表示。约束若只存在于注释、调用约定或某个 API 的校验中，就仍然可能被另一个写入口绕过；约束若由结构保证，读写路径都能从中受益。

案例二：客户合同与默认状态

客户可能有 fixed contracts，也可能处于 default contract。若使用 customers / contracts 表，并在 contracts 中同时存 fixed contract 与 default contract 的 rows，模型会允许一系列真实数据问题：合同之间出现 gaps，fixed contract 没有 end，以及 API 分别修改客户和合同时留下不一致状态。

可以移除 contracts 表中的 default rows：只有 fixed contract 才落表；当客户没有 fixed contract 时，就推断其处于 default。这样，没有合同覆盖的 gap 不再是可表示状态，同时 fixed contract 的 end 也不再需要 optional，因为它必须有明确的后继边界（或由领域定义的结束边界）。

这并不要求改变所有现有调用者的形状。若旧 API 需要看到 default contract rows，可以用 database view 将更精确的内部模型投影回旧形状；兼容性由投影承担，而不是让写模型重新承受冗余状态。

进一步的边界：overlap 到底是不是非法

连续不自动意味着不能 overlap。是否允许 overlap 必须先成为明确的领域决策：

  • 若 overlap 是非法的，可以在数据库层使用 excludes constraint（或等价的约束）拒绝相交区间，让并发写入也受到保护。
  • 若 overlap 是合法的，write model 可以保留重叠事实，read projection 再按消费者需要 flatten。不要为了得到好看的读取结果而静默丢弃信息。
  • 若业务规定后来的 fixed contract 会终止较早的合同，可以在读取或领域投影中表达这一关系；保留原始事实，避免直接 mutate 旧合同导致历史信息消失。

因此，让非法状态无法表示首先要求辨认哪些状态真的非法；模型不应替产品做未决定的选择。

实践检查清单

  1. 列出领域不变量：例如区间连续且不重叠``每个 fixed contract 有结束边界。区分真正规则与当前表结构的偶然结果。
  2. 找出重复事实：同一边界、default row、可由缺失状态推导的字段，是否能只保留一个来源？
  3. 检查每个写入口：API、批处理、迁移和并发事务是否都只能产生合法组合？
  4. 选择最小状态空间：优先使用集合、切分点、受约束的值类型或互斥分支，而不是若干可互相矛盾的字段。
  5. 区分写模型与读模型：对外兼容的旧形状可以由 view/projection 生成，不必反向污染规范化的写模型。
  6. 明确保留信息的策略：投影可以丢弃展示所不需要的信息，但原始模型不应为方便展示而不可逆地 mutate。
  7. 为边界写测试和数据库约束：特别覆盖相邻、gap、overlap、缺失结束边界以及并发写入场景。

边界与权衡

这条原则不是要求所有状态都静态编码，也不是消灭所有运行时校验。复杂规则可能更适合数据库约束、事务边界或构造阶段的智能检查；外部输入仍必须解析和拒绝。过度追求不可表示也可能让模型难以理解，或把本来合法的业务变化锁死。

数据库设计尤其要警惕 atomistic OO 思维：把每个概念都 reify 成一行，往往会复制同一事实并制造可独立更新的矛盾组合。关系模型的价值在于通过关系、约束和投影表达事实，而不是机械地把对象图中的每个名词都变成 row。最终应在不变量强度、查询便利、历史保留、迁移成本与并发安全之间取平衡。

启发点（关键洞察）

  1. 数据结构不是被动存储；它决定了系统可以表达哪些世界。减少表示空间，通常比增加校验分支更可靠。
  2. 冗余字段的风险不只是存储成本，而是它们可以彼此不同步；删除可推导事实往往同时简化写入和读取。
  3. 兼容旧 API 不等于保留旧写模型。projection/view 可以把规范化事实重新组织成调用者熟悉的形状。
  4. 非法是领域判断，不是形式上的偏好。overlap、历史合同是否保留等问题必须显式决策，不能由建模技巧偷偷决定。
  5. 好的 relational model 让约束靠近事实和数据库边界；面向对象的概念拆分不应凌驾于数据不变量之上。
