  • Q：怎样让一小段受约束的程序安全地在内核事件发生处执行，并与用户态交换数据？
  • A：eBPF 由用户态加载程序，经内核 verifier 验证后挂到 hook；程序通过 helper 使用内核能力，通过 map 保存或传递数据。

1. eBPF 是什么

eBPF 是 Linux 内核中的一种受约束执行环境。用户可以把小型程序加载到内核，并让它在指定事件发生时运行，而不必修改内核源码或编写传统内核模块。

它不是常驻后台进程，也不是可以任意调用内核函数的通用虚拟机。一个 eBPF 程序通常只做一件事：收到 hook 提供的上下文，读取或更新少量状态，然后返回一个结果。内核可将程序 JIT 编译为本机指令，也可解释执行。

2. 执行链路

verifier 在程序运行前做静态检查，例如确认控制流可终止、内存访问有边界、寄存器和指针类型合法。验证通过不等于业务逻辑正确，只表示内核认为这条执行路径满足安全约束；失败时应先阅读 verifier log。

3. 四个核心角色

  • program：事件触发时执行的受限逻辑。程序类型决定可用上下文、返回值语义和可调用的 helper。
  • hook：程序的触发点，例如 tracepoint、kprobe、网络接口的 XDP/TC、cgroup 或 LSM hook。选择 hook 就是在选择“何时运行”和“能看到什么”。
  • map：内核管理的键值数据结构，可供 eBPF 程序和用户态共享。常用于计数、配置、关联跨事件状态；并发更新时仍要考虑原子操作、per-CPU map 等同步语义。
  • helper：内核提供的受控函数入口，例如读取时间、查找 map、输出事件。程序不能随意调用内核函数；可用 helper 取决于程序类型和内核版本。

心智模型可以简化为：hook 决定何时运行，program 决定做什么，helper 提供受控能力，map 保存并传出状态。

4. 典型用途

  • 可观测性：统计系统调用、函数延迟、网络丢包和调度事件。
  • 网络处理：在 XDP/TC 等路径进行过滤、转发、负载均衡或流量统计。
  • 安全审计与策略：观察进程行为，或在 cgroup/LSM 等 hook 上执行策略。
  • 性能分析：采样调用栈、定位热点和异常延迟。

eBPF 适合事件驱动、短时且数据量可控的内核侧逻辑；复杂聚合、持久化和展示通常应留在用户态。

需要开发可部署程序时，再沿着以下路径前进：

  1. 优先选择 tracepoint 等相对稳定的 hook，明确输入上下文与输出数据。
  2. 用受支持的前端生成 BPF 字节码，用 loader 创建 map、加载并 attach 程序。
  3. 在用户态读取 map 或 ring buffer，并负责聚合、展示和生命周期管理。
  4. 面向多内核版本部署时，考虑 BTF 与 CO-RE，并在目标内核上实际验证。

6. 限制与注意事项

  • 内核与权限相关：程序类型、helper、BTF 和 attach 方式随内核版本及配置变化；加载通常需要 root 或相应 capabilities。
  • 验证器约束：所有路径必须可证明安全；栈空间较小，循环、指针运算和动态内存访问受严格限制。错误处理和边界检查不能省略。
  • 运行开销仍然存在：高频 hook、复杂逻辑、逐事件向用户态发送数据都可能明显影响系统，应尽量在内核侧过滤或聚合，并监控丢事件。
  • hook 稳定性不同：kprobe 依赖内核函数及其实现细节，跨版本更脆弱；tracepoint 通常更稳定。不要把“可 attach”误认为接口长期兼容。
  • 并发与生命周期：程序会在多个 CPU 上并发执行；map 容量、更新竞争、对象 pinning、detach 和清理都需要显式设计。
  • 安全边界不是绝对隔离：verifier 显著降低风险，但内核漏洞或错误使用仍可能影响整机；生产环境应最小化权限、程序复杂度和 hook 范围。
