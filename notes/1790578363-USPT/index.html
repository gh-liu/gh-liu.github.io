OverlayFS 的分层视图、copy-up、whiteout、挂载约束与工程边界

  • S：容器镜像、只读系统和临时开发环境需要复用一份不可变基础树，同时让每个实例拥有独立的可写视图。
  • C：直接复制完整目录成本高；但把多层目录叠加后，读取、修改、删除和重命名都不能再简单等同于操作单个文件系统。
  • Q：OverlayFS 如何把多棵目录树呈现为一个统一视图，并在不修改 lower layer 的前提下支持写入？
  • A：OverlayFS 按优先级合并目录项：读时选择最上层可见对象，首次修改 lower 对象时按需 copy-up，删除则在 upper 中记录 whiteout；它节省的是初始复制和共享存储成本，代价是首次写放大、对象身份变化以及若干非标准语义。

1. 心智模型

OverlayFS 是 Linux 的联合挂载（union mount）实现。它不把各层物理合并，而是在 VFS 层提供一个组合后的命名空间。

  • lowerdir：一个或多个底层目录。可以只读，也可以是另一个 OverlayFS；共享 lower 是常见用法。
  • upperdir：记录新增文件、copy-up 后的文件以及删除标记。没有 upper 时，合并视图只读。
  • workdir：OverlayFS 完成 copy-up、rename 等操作时使用的内部目录，必须与 upper 位于同一文件系统，且应为专用空目录。
  • merged / mount point：应用实际访问的统一视图。应用不应绕过它直接修改正在使用的各层。

2. 查找与目录合并

查找路径时，OverlayFS 从高优先级层向低优先级层解析每一级名称：

  1. 同名对象只在一层存在：使用该对象。
  2. upper 和 lower 都存在，且至少一个不是目录：upper 对象遮蔽 lower 对象。
  3. upper 和 lower 都是目录：形成 merged directory，继续合并两边的目录项。

目录合并只合并名称列表。合并目录自身的权限、时间戳和扩展属性等元数据来自 upper 目录，而不是把上下层元数据再做合并。

读取 merged directory 时，内核先读 upper，再补入未出现过的 lower 名称，并为本次打开的目录缓存结果。因此：

  • 目录保持打开期间，其他修改不一定立即反映在该次 readdir 中；回到 offset 0 后重新读取会重建缓存。
  • 目录 offset 是合并时临时分配的；关闭目录、内容变化、重新打开后，旧 offset 不保证仍指向相同位置。

3. 写入：copy-up

lower 对象保持不变。对 lower 中的非目录对象执行需要写权限的操作时，OverlayFS 先把对象复制到 upper，再在 upper 上完成操作，这个过程称为 copy-up。

常见触发条件包括：

  • 以可写方式打开文件，即使最终没有真正写入；
  • 修改数据或执行 truncate；
  • 修改 owner、mode、时间戳或扩展属性；
  • 为 lower 文件创建 hard link。

copy-up 大致执行：

父目录会按需复制，但复制目录不等于递归复制其全部内容；未修改的子项仍可来自 lower。默认情况下，单纯 chmod 一个大文件也可能复制完整数据。启用 metacopy=on 后，元数据操作只先复制元数据，直到真正写数据时才复制文件内容。

copy-up 的工程影响：

  • 首次写延迟和写放大：大文件的第一次修改可能先复制整个文件。
  • 空间占用：修改后的完整对象位于 upper；OverlayFS 不是块级增量存储。
  • 身份变化：对象可能从 lower inode 切换为 upper inode，st_dev / st_ino 不应被当作永远稳定的业务标识。
  • hard link 语义：未启用 index 时，copy-up 一个有多个名称的 lower inode 可能打破名称间的 hard-link 关系。

metacopy 优化的是只改元数据的场景，并不消除真正写入时的数据 copy-up；也不应对不可信的 upper/lower 启用，因为伪造的 overlay 扩展属性可能让数据重定向到非预期 lower 文件。

4. 删除：whiteout 与 opaque directory

删除 merged 视图中的 lower 文件时，OverlayFS 不能真的删除 lower 文件，否则其他共享该 lower 的挂载也会受影响。因此它在 upper 中写入一个不可见的“这里已经删除”标记。

Whiteout

whiteout 遮蔽 lower 中的同名对象。它在 upper 中通常表示为：

  • 设备号为 0/0 的字符设备；或
  • 带 trusted.overlay.whiteout 扩展属性的零长度普通文件。

查找时，OverlayFS 既不显示 whiteout，也不再显示它遮蔽的 lower 对象。

Opaque directory

upper 目录带 trusted.overlay.opaque=y 时，该目录是 opaque 的：同路径的 lower 目录及其内容完全不参与合并。这与 whiteout 只隐藏一个同名目录项不同。

因此，“在 merged 中删除后 lower 仍存在”不是数据删除失败，而是 OverlayFS 的设计。备份、迁移或制作镜像层时，必须保留 whiteout、opaque 标记和相关 xattr；只复制普通可见文件会改变语义。

5. 重命名

  • 纯 upper 文件或目录可直接在 upper 中重命名。
  • lower 文件通常先 copy-up，再完成重命名。
  • lower 或 merged 目录的跨目录 rename 默认可能返回 EXDEV。许多工具（如 mv）会退化为递归复制再删除，但应用不能假设 rename 始终原子且廉价。

启用 redirect_dir=on 后，OverlayFS 可以只 copy-up 目录本身，在 upper 目录上记录 trusted.overlay.redirect 指向原 lower 路径，再移动 upper 目录；这样避免立即复制整棵子树。redirect 会增加持久化层之间的关联和安全校验要求，复制或替换 layer 时不能忽略这些 xattr。

6. 挂载约束与关键选项

文件系统约束

  • upper 必须支持 trusted.* 或 user.* 扩展属性，并在 readdir 中提供有效的 d_type；NFS 因此不适合作为可写 upper。
  • workdir 必须与 upper 在同一个底层文件系统。
  • lower 不要求可写，可以有多个，也可以是另一个 OverlayFS。
  • upper/workdir 不能同时被多个 OverlayFS 挂载复用或重叠；此类访问的行为未定义。
  • 挂载期间直接修改 lower、upper 或 workdir 的行为未定义。所有正常访问都应经过 merged。

常见选项

选项 解决的问题 代价 / 注意点
metacopy=on 元数据修改时延迟复制文件数据 真正写入仍需 copy-up；不能信任恶意 layer
redirect_dir=on lower/merged 目录 rename 不必返回 EXDEV 增加 redirect xattr 和跨层关联
index=on copy-up 后维护 hard link 和 lower-origin 关系 需要底层支持持久 file handle，会增加索引元数据
xino=on/auto 组合 fsid 与底层 inode，使 inode 标识更接近普通 FS 依赖 inode 位宽和底层能力，溢出时会退化
userxattr 使用 user.overlay.*，支持非特权挂载场景 安全模型与 trusted xattr 不同
volatile 跳过 upper 的同步写，降低写入开销 崩溃后不保证可恢复，只适合可重建数据

实际默认值还会受内核版本、构建选项和 module parameter 影响。判断当前挂载行为时，应查看 /proc/self/mountinfo、findmnt -t overlay 以及 /sys/module/overlay/parameters/，不要只依赖发行版文档中的默认值。

7. 一致性、权限与非标准语义

权限

OverlayFS 会进行两层检查：

  1. 当前进程是否能按 merged inode 的 DAC/MAC 信息访问对象；
  2. 创建 OverlayFS superblock 时保存的凭据，是否能在实际 upper/lower 上执行该操作。

目标是让 copy-up 前后的访问结果尽量一致，同时防止挂载者借 OverlayFS 获得其原本没有的底层权限。排查“merged 看似有权限但操作仍失败”时，也要检查底层目录和挂载凭据。

inode 与设备号

OverlayFS 是 hybrid filesystem：目录通常报告 overlay 的 st_dev，非目录对象可能报告其实际 upper/lower 文件系统的 st_dev；非目录对象的 st_ino 也可能因 copy-up 变化。所有 layer 在同一文件系统，或可用 xino 时，表现会更接近普通文件系统。

依赖 (st_dev, st_ino) 的扫描器、备份工具、文件监控和 NFS export 需要专门验证，不能从 ext4/xfs 的经验直接推导。

已知差异

OverlayFS 大体兼容 POSIX，但不是完全透明，内核文档明确列出一些差异，例如：

  • 读取仍位于 lower 的文件时，不更新其 st_atime；
  • lower 文件以只读方式打开并 MAP_SHARED 映射后，之后对该文件的修改不会反映到既有映射；
  • lower 文件正在执行时，对它写入或截断不一定像普通文件系统那样返回 ETXTBSY。

此外，崩溃一致性仍依赖应用正确调用 fsync。OverlayFS 会避免暴露 copy-up 的中间文件，但默认并不承诺在应用未同步时持久化所有目录和纯元数据修改；volatile 更是明确放弃崩溃恢复保证。

8. 与容器镜像的关系

OverlayFS 的模型与容器的分层文件系统天然匹配：多个只读镜像层作为 lower，容器自己的可写层作为 upper，再把 merged 作为容器看到的 root filesystem。

这解释了几个常见现象：

  • 启动容器不必复制整个镜像；不同容器可以共享只读 layer。
  • 容器内修改镜像中的大文件会触发 copy-up，可能出现首次写延迟和额外空间占用。
  • 容器内删除镜像文件只在可写层生成 whiteout，不会改动镜像层。
  • 删除容器的 writable layer 后，所有未写入 volume/bind mount 的变更也随之消失。

OverlayFS 只提供分层文件系统机制；镜像格式、layer 下载、内容寻址、快照生命周期和 volume 管理由 container runtime / snapshotter 等上层组件负责，二者不能等同。

10. 总结

用三条规则即可先建立正确直觉：

  1. 读：最上层同名对象获胜，目录可以继续合并。
  2. 写：lower 不变，首次修改先 copy-up 到 upper。
  3. 删：lower 不变，在 upper 用 whiteout / opaque 记录不可见性。

然后再根据工作负载评估 copy-up 成本、inode 身份、hard link、rename、崩溃一致性和底层文件系统能力。OverlayFS 的优势不是让写入免费，而是让大量只读内容能够共享，并把每个实例的差异集中到较小的可写层。
