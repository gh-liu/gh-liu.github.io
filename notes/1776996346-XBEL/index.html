用 invariant 压缩系统演化的时间维度，并指导小尺度代码与大尺度系统设计。

https://matklad.github.io/2023/10/06/what-is-an-invariant.html

  • 是什么（What）
    • Invariant 是系统动态演化期间始终成立的性质。
    • 作者用 invariant 指三类概念：区分模糊想法与精确命题的数学思维、小尺度编程中保证代码正确的技术，以及大尺度编程中紧凑、具有传播性、描述系统的性质。
  • 为什么（Why）
    • 程序或代码库随时间演化时，可能路径会组合爆炸；逐条推演既困难又容易漏掉边界条件。
    • Invariant 压缩了系统描述、消除了时间维度，只保留所有路径共享的性质，因此能让我们基于明确理由写对细节，并维持大型系统统一的心智模型。
  • 怎么做（How）
    • 先精确定义结果，再写出每次循环或递归前后都必须成立的约束；初始化要建立约束，每一步要保持约束并缩小问题，结束时由约束推出结果。
    • 让条件分支直接对应 invariant。若只能靠试错添加 +1、-1 或特殊分支，通常说明约束还没有表达清楚。
    • 在系统设计中选择少量紧凑的性质，并让所有代码持续遵守；同时评估其传播成本，因为不合适的 invariant 也可能令常见场景更复杂。

核心观点：

Invariant 是系统动态演化过程中始终成立的性质。它用所有可能轨迹共享的性质压缩系统描述： 小尺度上帮助把算法细节接对，大尺度上帮助简单系统在扩展为生产系统时仍保持可推理。

小尺度：二分查找插入点

目标是实现 insertion_point(xs, x)：返回最小索引，使 x 插入该位置后数组仍有序。

作者先给出穷举测试：生成短的已排序数组和目标值，检查返回位置左侧严格小于 x，右侧大于等于 x。这种测试能暴露仅凭经验法则写出的二分查找在重复元素或极小区间上的问题。

当 xs[mid] < x，mid 也确定属于左侧区域，因此下界是 mid + 1；否则 mid 可能就是首个大于等于 x 的位置，只能令 hi = mid。初版在 x >= xs[mid] 时令 lo = mid：若 x == xs[mid]（甚至相邻元素也等于 x），既破坏 lo 左侧严格小于 x 的 invariant，也可能无法缩短区间。

重点不在这一条二分查找公式，而在通用方法：先精确说明结果，再把它写成循环或递归 invariant，才能因正确的理由写对边界细节，而非得到一个大致能用的算法。

大尺度：约束代码库演化

小尺度关注运行时状态随迭代演化；大尺度关注源代码随重构和新功能演化。系统 invariant 会传播到整个代码库：它简化一类问题，也要求每处实现共同承担约束。

  • Cargo：保留用户输入的路径。 用户传入 ../some/dir 时，不擅自 canonicalize 为绝对路径，而是原样交给操作系统。文件系统中看似等价的路径不一定等价；这个 invariant 很紧凑，近似于禁止调用 fs::canonicalize。
  • rust-analyzer：语法树是无 identity 的值类型。 一个 if 表达式节点自身不知道位于哪个文件哪一行，调用方需额外携带来源信息。这让重构 API 更原则化，却影响所有代码；作者反思这可能是错误取舍，因为语言服务器更常做只读分析，或许应把 identity 纳入核心结构，并只为重构产生的临时树使用假 identity。
  • rust-analyzer：IDE 看见完整、冻结的当前世界快照。 API 表现得像所有类型等派生数据始终已计算，也不显式暴露代码变更或历史版本；底层再按需计算并复用旧结果。这提供了简单心智模型，也清楚分隔编译器核心和重构、补全等 IDE 功能。
  • TigerBeetle：启动后不分配内存。 所有逻辑必须使用预分配结构，因此每样东西都有明确数值上限，也不能假设存在可供 memcpy 的环境空间。
  • TigerBeetle：事务逻辑不读磁盘。 事务可能接触的对象必须事先预取到内存，从而可为整批事务并行执行 IO，再用无锁的紧凑串行 CPU 循环执行事务。
  • TigerBeetle：上层所见的磁盘读取不会失败。 读取 API 接收块地址和 checksum，只回调 checksum 匹配的数据；本地读取失败时由其他副本透明修复。若可达副本都没有目标块，集群会正确地停住等待，而不是把错误处理扩散给每层调用方。

启发点（关键洞察）：

  1. 漂亮的接口、对称命名、半开区间和无特判等经验法则不能代替正确性证明；分支必须逐项保持明确的 invariant。
  2. Invariant 的价值是压缩时间：不枚举无限条执行或演化轨迹，而是推理所有轨迹共享的少数性质。
  3. 系统 invariant 具有传播性。好的约束把复杂机制藏在稳定边界后面；错误的约束则会让全系统为低频场景付费，所以必须结合常见工作负载评估。
  4. 小尺度和大尺度是同一种思维：前者约束程序状态的演化，后者约束代码库本身的演化。
