The Dataflow Model: A Practical Approach to Balancing Correctness, Latency, and Cost in Massive-Scale, Unbounded, Out-of-Order Data Processing

  • 是什么（What）：
    • 一个处理无界、乱序数据的统一编程模型。它将数据处理拆成 What / Where / When / How 四个相互独立的维度，以窗口、触发器和增量修订表达业务语义。
  • 为什么（Why）：
    • 对无界数据，系统通常无法证明数据已经完整；若把 watermark 当作完成信号，就会在低延迟、正确性和成本之间做出隐式且僵化的取舍。
    • 批处理、微批和流处理是执行方式，不应决定业务语义。相同的逻辑处理计划应能运行在不同引擎上，仅体现延迟和资源成本的差异。
  • 怎么做（How）：
    • 用 event time 和 window 定义数据属于哪个逻辑结果；用 trigger 定义何时物化阶段性结果；用 discarding、accumulating、retracting 定义新旧结果的关系。

核心问题

无界、乱序数据使等待全部数据后再给出唯一答案失去可操作性。问题不只是输入永不结束，还在于业务时间与系统处理时间天然错位：系统既无法准确判断结果何时完整，也无法同时得到最低延迟、最高正确性和最低成本。

1. 无界数据没有可靠的结束

日志、移动端事件和传感器数据持续产生，并且会因离线设备、网络延迟、重试、调度和反压而乱序到达。即使某个时间段暂时没有新事件，也无法由此证明未来不会再收到属于该时间段的数据。

因此，对无界数据问什么时候收齐全部输入通常是一个不可判定的工程问题。更实用的问题是：

  1. 当前已知数据能得到什么答案？
  2. 什么时候值得把这个答案交给下游？
  3. 新数据到来后怎样修正旧答案？
  4. 为更快或更准确的答案，愿意付出多少计算、存储和运维成本？

2. Event time 与 processing time

  • Event time：事件实际发生的时间，来自事件本身；用于回答业务事实发生在什么时候。
  • Processing time：事件在流水线某个节点被观察和处理的时间；用于回答系统什么时候知道这件事。

事件的 event time 通常不变，但它在流水线各处的 processing time 不断变化。两者之差来自网络、排队、重试、处理耗时等因素，而且会动态波动。

若按 processing time 分窗，迟到事件会被计入到达时的窗口，重放同一批数据还可能得到不同结果。按 event time 分窗才能稳定地还原事件发生时的业务上下文。

设计思想

Dataflow Model 不再寻找统一的完成时刻，而是将计算内容、事件时间范围、输出时机和修订关系拆开，使每个维度都能独立表达和组合。

核心思想：让结果持续演化

不要等待无界数据最终完整，而要让结果能够随新事实持续演化，并把正确性、延迟和成本的取舍显式交给使用者。

Dataflow Model 最重要的贡献不是流处理比批处理更好，而是把数据集的性质与执行引擎的形态分开：

  • 数据集是 bounded / unbounded；
  • 执行引擎才是 batch / micro-batch / streaming；
  • 无界数据可以由重复批处理执行，有界数据也可以由流式引擎执行；
  • 在语义足够完整的模型下，三类引擎可以计算相同的正确结果，区别主要落在延迟和成本上。

论文用四个问题描述一条数据处理流水线：

问题 含义 Dataflow 中的机制
What 计算什么结果？ ParDo、GroupByKey、聚合等变换
Where 在 event time 的什么范围内计算？ Window assignment / merging
When 在 processing time 的什么时刻输出？ Trigger
How 后续结果如何修订先前结果？ Discarding / Accumulating / Retracting

这四个维度正交后，同一种业务计算可以自由组合窗口、输出时机和修订策略，而不用复制一套 batch 逻辑和一套 streaming 逻辑。

What：核心变换

论文从两个基本变换出发：

  • ParDo：对每个输入调用用户函数，产生零到多个输出。它逐元素工作，可以自然处理无界输入。
  • GroupByKey：收集同一 key 的所有 value。对无界输入，所有永远没有自然边界，因此实际需要的是 GroupByKeyAndWindow。

Window 不是一种可选的性能优化，而是让无界数据上的聚合、外连接等操作具有有限作用域的语义边界。map、filter、内连接等不必等待一组数据完整的操作则不一定需要窗口。

Where：窗口决定事件时间上的分组

常见窗口包括：

窗口 定义 特征 典型场景
Fixed / Tumbling 固定长度且不重叠 通常 aligned 每小时请求量、每日账单
Sliding 窗口长度 + 滑动周期 可重叠，一个事件可属于多个窗口 最近一小时、每分钟更新
Session 相邻活动间隔小于 gap 就合并 按 key 形成，unaligned 用户会话、设备活跃区间

Aligned window 对所有 key 使用同一组边界；unaligned window 只作用于某个数据子集，例如每个用户的 session 边界各不相同。论文将所有窗口在模型层统一视为 unaligned，再由执行层优化 fixed 等 aligned 场景。

窗口被拆成两个操作：

  1. AssignWindows(element) -> Set<Window>：根据元素及其 event time，把元素分配到零到多个窗口；
  2. MergeWindows(Set<Window>) -> Set<Window>：在分组时合并窗口，使数据驱动的窗口可以随新事件演化。

Watermark：进度估计，不是完整性证明

Watermark 可理解为系统认为已经处理到的 event time 下界：当 watermark 为 t 时，系统估计 event time 小于 t 的数据大多已到达。

它很有用，但存在两个相反的问题：

  • 太快：watermark 已越过窗口末尾，迟到数据仍可能出现，已有结果需要修订；
  • 太慢：一个 straggler 可能拖住全局进度，使绝大多数正常数据迟迟不能输出。

所以 watermark 适合：

  • 估计窗口何时足够完整；
  • 监控 pipeline 的 event-time lag 和健康状态；
  • 驱动允许近似的输出与状态垃圾回收策略。

但它不应该被解释为此后绝不会再有旧数据。对于离线移动设备之类的输入，系统根本不知道设备何时重新上线；watermark 通常只能是启发式估计。结构化输入源若能暴露尚未处理的数据范围，watermark 可以非常准确，但仍需区分高质量估计和逻辑证明。

When：Trigger 决定何时物化结果

Window 回答哪些事件属于同一个结果，trigger 回答什么时候观察这个结果。一次触发产生该窗口的一个 pane；同一个窗口可以产生多个 pane。

触发信号可以来自：

  • event-time progress：watermark 越过窗口末尾；
  • processing time：首个元素到达若干时间后，或周期性输出；
  • data driven：元素个数、字节数、数据模式等达到条件；
  • external signal：RPC 回调、外部进度指标、人工注入请求等。

How：增量结果如何相互关联

同一窗口多次触发时，Dataflow 提供三种 refinement mode：

模式 每次 pane 的含义 状态/成本 下游要求
Discarding 只包含上次触发后新到的数据 状态最少 下游能够合并独立增量，例如累加 delta
Accumulating 包含截至当前的全部数据，是旧结果的新版 需保留累计状态 下游按 key/window 覆盖旧值
Accumulating & Retracting 先撤销旧结果，再发出累计后的新结果 还需保存已发结果，成本最高 下游理解并传播 retraction

Retraction 在连续多个 grouping stage 时尤其重要。假设一个迟到事件把 session A 和 B 合并成 C，下游已经按 A、B 的属性做过二次聚合：仅发送 C 会让 A、B 的影响残留；必须先撤销 A、B，再加入 C，才能维持派生结果的正确性。

这种模式也有约束：简单实现依赖确定性计算；可逆 combiner 可通过 uncombine 高效撤销，否则需要保存更多状态或重算。最终 sink 也必须支持幂等覆盖、upsert 或显式撤回，否则模型内部的正确修订无法转化为端到端正确性。

四个维度的组合：视频观看会话

论文的动机案例是视频平台统计用户观看 session，用于实时分析和计费：

  1. What：按用户聚合观看时长、广告和视频信息；
  2. Where：按 event time 使用 30 分钟 gap 的 session window；
  3. When：周期性给出低延迟估计，watermark 越过 session 后给出较稳定结果，迟到数据到达后继续触发；
  4. How：使用 accumulating & retracting，使离线设备补传数据后能够合并 session，并撤销下游已消费的旧结果。

这一表达同时适用于实时处理和历史 backfill；切换执行引擎不应要求重写业务逻辑。

工程取舍

模型没有消除现实约束，而是把 correctness、latency 与 cost 的冲突从执行引擎的隐式行为，提升为使用者能够审视和配置的显式策略。

输出策略如何改变正确性、延迟与成本

不同输出与状态策略对应不同的取舍：

选择 延迟 正确性/新鲜度 成本
只在 watermark 后输出 较高，受 straggler 影响 首次结果通常更稳定，但仍非绝对完整 输出和下游更新较少
增加 early trigger 较低 先给近似结果，随后修订 更多计算、状态、网络和 sink 写入
接受任意迟到数据 可能持续修订 更接近最终事实 状态无法轻易回收，成本高
限制 lateness / 清理状态 可控 超过期限的数据无法纳入原结果 存储和运维成本可控
使用 retraction 可维护多级派生正确性 能撤销旧事实 协议、状态和下游处理最复杂

正确性也不是单一开关。它至少取决于输入可重放性、事件去重、状态一致性、用户函数确定性、trigger/refinement 语义以及 sink 是否正确应用更新。论文提供的是组织这些选择的模型，不会自动解决端到端 exactly-once。

同一语义在不同执行引擎上的表现

相同的 event-time window + watermark trigger 可以映射到不同引擎：

  • Batch：watermark 在处理期间停留在时间起点，输入完成后推进到无穷大，一次性物化窗口；
  • Micro-batch：每个批次形成一次进度推进，变更过的窗口按批次更新；
  • Streaming：watermark 随输入进度持续推进，窗口及时输出，迟到数据触发修订。

这三者可以具有相同的逻辑语义。真正的工程差异是调度粒度、状态管理、输出频率，以及由此产生的延迟和资源成本。论文也由此反对 Lambda Architecture 中长期维护两套业务实现：统一模型允许一套逻辑在实时运行和大规模 backfill 之间复用。

设计原则与实践依据

论文总结了五条设计原则：

  1. 永远不要依赖数据完整的概念；
  2. 保持灵活，以容纳不同及未来未知的用例；
  3. 模型在 batch、micro-batch、streaming 上都应有意义并带来价值；
  4. 鼓励清晰的实现；
  5. 支持在事件实际发生的上下文中稳健分析数据。

这些机制来自 Google 使用 FlumeJava 和 MillWheel 的实际经验：

  • 大规模 log join 与 backfill 推动 batch/streaming 统一；
  • 搜索、广告、分析、社交和 YouTube 的用户活动推动 unaligned session window；
  • 计费系统中的迟到数据和 watermark lag 推动 trigger、accumulation、retraction；
  • 统计与 abuse detection 推动 watermark 和 percentile watermark trigger；
  • 推荐系统偏好及时的局部视图，推动 processing-time trigger；
  • 异常检测需要发现后立即输出，推动 data-driven 与 composite trigger。

适用边界与隐含代价

  1. 这是编程模型，不是性能突破。 CPU、内存、磁盘、网络的物理约束仍然存在；高频 trigger 和长期接收迟到数据会直接转化为更高成本。
  2. Watermark 的质量依赖输入源。 模型允许处理错误估计，却不能凭空知道尚未出现的数据。状态何时清理仍需业务策略。
  3. 论文弱化了实现细节。 核心代码在 FlumeJava、MillWheel 和当时的 Cloud Dataflow 中实现，但论文没有深入说明状态布局、容错、定时器扩展性和 retraction 成本。
  4. 端到端修订需要下游协议配合。 只要 sink 或后续系统把每个 pane 当作互不相关的新记录，accumulation/retraction 的语义就会丢失。
  5. 统一语义不等于运行行为完全一致。 不同引擎的 watermark 推进、调度粒度和故障恢复方式仍会造成可观察的输出时机及成本差异。
  6. 论文中的 API 是 2015 年的简化 Dataflow Java SDK。 应把示例当作语义说明，而不是当前 Apache Beam API 的精确用法。

启发点（关键洞察）：

  1. 完整性不是事实，而是策略。 在开放世界中，系统不能证明未来没有迟到数据；它只能基于当前知识决定何时输出、何时修订、何时停止维护状态。
  2. Window 与 trigger 必须分开。 业务上哪些事件属于一起和系统何时给答案是两个不同问题；将它们绑在一起会迫使语义服从执行机制。
  3. Watermark 是知识边界。 它描述系统对 event-time 进度的估计，而不是数据世界的客观终点。把它当作监控和触发信号比当作完成证明更准确。
  4. 结果应被视为随时间演化的值。 多个 pane 不是重复答案，而是同一逻辑结果的增量、替换或撤回。这与数据库的 change stream / changelog 思想相通。
  5. 低延迟的本质是提前暴露不完整信息。 早出结果并不免费：下游必须能够理解修订，系统必须承担更多状态和更新成本。
  6. 正确性是端到端协议。 Source、状态、用户计算、触发策略和 sink 中任一环节不支持重放、去重或修订，都可能破坏整体语义。
  7. Batch 是 streaming 的退化情形。 有界数据可看作 watermark 最终推进到无穷大的无界计算；这种视角简化了实时计算、历史重放和 backfill 的统一设计。
