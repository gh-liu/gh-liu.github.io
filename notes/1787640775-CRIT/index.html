基于 primary copy 的复制协议：用 viewstamp 廉价判断视图变更后哪些信息幸存，正常路径性能接近未复制系统

https://www.cs.princeton.edu/courses/archive/fall11/cos518/papers/viewstamped.pdf Oki & Liskov, PODC 1988（后续 2012 年有 Liskov & Cowling 的 VRR 修订版）

  • 是什么（What）：
    • 一种基于 primary copy 技术的复制算法，用于构建高可用分布式服务。以模块（服务器）为复制单元：模块的若干副本（cohort）组成模块组（group），其中一个被指定为 primary，其余为 backups；primary 执行所有远程调用，backups 后台被动接收状态。
    • 引入特殊时间戳 viewstamp = (viewid, timestamp)，用于廉价判断一次视图变更（view change）后哪些事务信息幸存：幸存则可继续 commit，否则 abort。
    • 正常路径下远程调用的延迟与未复制系统相同；崩溃或分区时执行 view change 选出新 primary，恢复服务。
  • 为什么（Why）：
    • 动机：高可用只能靠复制；原始的 primary copy 方法要求能区分节点故障与网络故障，而现实中两者不可区分，且原方法在故障下会丢失大量信息。目标是在一般网络（节点崩溃 + 分区）下工作，同时做到：事务交互延迟小、视图变更丢失信息少。
    • 核心权衡：在「故障时丢失的工作量」与「系统需携带的额外信息量」之间折中。Isis 是极端之一（故障不丢工作，但每条消息携带大量信息、难以垃圾回收）；无时间戳的系统是另一极端（故障时把所有受影响事务一律 abort）；viewstamp 是中间点：只携带"哪些事件已发生"的紧凑信息，代价是 prepare 时可能等待 force、偶尔因信息丢失而 abort。
  • 怎么做（How）：
    • 事务处理：远程调用只在 primary 执行（性能与非复制一致）；每完成一个调用，primary 向通信缓冲（buffer）写入一条事件记录（completed-call / committing / committed / aborted / done），事件按 timestamp 序可靠送达 backups。prepare 时用 compatible(pset, history) 判断本副本是否知道该事务在本组的所有调用，并用 force-to 把相关事件强制到 sub-majority 的 backups，保证 commit 决策在视图变更后仍可兑现。
    • 视图变更：副本间周期发送 "I'm Alive" 心跳；检测到通信变化或从崩溃恢复即触发 view change。view-manager 生成更高 viewid 并发邀请，收集各副本的接受响应（normal 接受携带 viewstamp；crash 接受表示丢失了 gstate）；满足视图形成规则后，选返回最大 viewstamp 的副本为新 primary（尽量复用旧 primary），新 primary 用 newview 事件记录初始化其余副本。
    • 边界（该做与不该做）：旧 primary 在分区中仍可响应客户端，但永远无法 commit（无法把事件 force 到 backups），正确性不依赖"单一主"假设；协议不耐丢消息与慢响应，需用较长超时 + 重复消息避免连环视图变更；多数副本同时崩溃（catastrophe）时系统可能永远无法再形成新视图，因此 cur-viewid 等少量状态仍需落盘。

核心问题（问题演化）：

  1. 如何让复制在正常路径上几乎无开销（延迟接近未复制系统）？
  2. 节点故障与网络分区不可区分时，如何安全、快速地选出新 primary？
  3. 视图变更后，如何廉价判断哪些事务信息幸存——幸存者可继续 commit，而不必一律 abort？
  4. 事务提交与视图变更如何交互，才能保证 one-copy serializability（复制后的并发执行等价于未复制数据上的串行执行）？
  5. 复制能在多大程度上替代 stable storage？

设计思想（核心抽象）：

  1. Primary copy + 后台同步：调用只在 primary 执行，事件记录经通信缓冲按 timestamp 序发给 backups；正常路径零复制开销，成本被推迟到 prepare/commit 时。
  2. View 与 viewid：view 是当前（或曾经）可互相通信的副本集合 + primary 指示，必须包含配置的多数；viewid 全序唯一，视图变更即生成新 viewid。事务只在 active view 中处理。
  3. Viewstamp 与知识蕴含序：timestamp 仅在视图内有意义，拼接 viewid 得到全局唯一的 viewstamp。事件按 timestamp 序传播 ⇒ 同一视图内拥有更晚 viewstamp 的副本，知道更早 viewstamp 副本所知的一切——这是视图变更能一轮完成的关键。
  4. Sub-majority 与 force-to：sub-majority = 比配置多数少一；sub-majority backups + primary 自身即构成配置多数。「多数副本知悉 ⇒ 事件幸存到后续所有视图」由视图变更保证，事务可提交仅当其所有事件被多数知悉。
  5. History + pset + compatible()：每个副本维护 history（已知事件的 viewstamp 序列）；事务运行时收集 pset（每次远程调用获得的 (groupid, viewstamp) 对）。prepare 时用二者判断副本是否知道事务的全部调用，从而决定接受或拒绝 prepare。
  6. 视图形成规则：多数副本接受邀请，且信息充分——要么多数 normal 接受，要么 crash 接受的视图更旧，要么 crash 视图的 primary 做了 normal 接受（primary 至少知道 backup 所知的一切）。

工程取舍（为什么这样设计）：

  1. 为什么用 buffer + 事件记录替代 stable storage：正常路径写 volatile buffer、后台同步，避免每次调用都写盘；只有 prepare/commit 的关键时刻才 force-to 到 backups，把写稳定存储的延迟换成（通常更快的）网络往返。
  2. 为什么 commit 只等 sub-majority：sub-majority backups + primary = 配置多数，多数知悉的信息在任意后续视图中必然有副本携带，这是正确性与性能的最小交集。
  3. 为什么新 primary 优先选旧 primary：同副本连任则不丢任何进行中的工作（连未完成的远程调用都可继续）；即使换人，也保证旧视图中已 prepare 的事务可 commit、已 commit 的保持 committed。
  4. 为什么允许旧 primary 在分区中继续响应：它无法把事件 force 到 backups，因而无法 prepare/commit 任何事务——安全性不依赖"必须只有一个主"，从而避免了故障类型的区分。
  5. 为什么只持久化 cur-viewid 等极少量状态：作者有意探究"复制能在多大程度上消除 stable storage"；代价是多数副本同时崩溃可能造成灾难性丢状态，需按灾难概率与应用重要性权衡（复制本身已降低该概率）。
  6. 为什么用长超时 + 重复消息：视图变更不容忍丢消息/慢响应——提前排除潜在成员会立刻引发下一轮视图变更，形成连环抖动。
  7. 为什么引入嵌套事务（子事务）：远程调用无响应会导致整个事务 abort（无法判断重发是重复执行），丢失大量工作；把调用作为子事务执行，视图变更时只重做子事务，成本远低于探测与强制 start-call 记录。
  8. 为什么读锁也必须在 prepare 时 force：不 force 等于没给只读参与者发 prepare 消息；视图变更后新 primary 可能不知道旧读锁而允许冲突加锁，破坏两阶段锁定的正确性。

启发点（关键洞察）：

  1. 多数交集引理：任意两个多数必然相交，「事件被多数知悉 ⇒ 事件在后续所有视图幸存」是复制协议正确性的地基，raft 的日志提交与之同构。
  2. 知识蕴含序让视图变更一轮完成：virtual partitions 协议需三阶段，VR 用 viewstamp 在第一轮就确定"谁知道的最多"，直接选其当 primary，避免了额外通信。
  3. 把成本推到故障路径：正常路径零开销（调用只在 primary）、故障路径才付出 force 与 abort 代价——性能设计上"正常情况优先"的经典示范。
  4. 区分"信息幸存"与"信息丢失"，而非一律 abort：pset + history 精确回答"prepare 是否安全"，从而在视图变更后保留可提交的事务，只 abort 真正丢失信息的事务。
  5. 与 Raft 的渊源：Raft（2014）本质上是 VR 的简化与再工程——term ≈ view，log 全序 ≈ timestamp 序，Leader Completeness ≈ "新 primary 必含多数已提交信息"。读 VR 能更好地理解 Raft 的每个设计决策从何而来。
  6. 信息量与可用性的频谱：Isis 携带全部信息换取故障零 abort，无时间戳系统零信息但故障即 abort，viewstamp 是两者之间信息-成本的最优折中；选择落在哪一点取决于应用对 abort 的容忍度。
  7. 旧 primary 能响应但不能提交：安全性不靠"唯一定主"，而靠"无法 force 到多数 ⇒ 不可能 commit"——这是理解复制系统安全边界的一个很好的心智模型。
