从页、B-Tree、LSM、WAL 到复制、事务与共识，理解现代数据库的存储和分布式内核

https://book.douban.com/subject/35078474/

  • 是什么（What）：
    • 一本解释现代数据库底层实现的系统性导读。上半部分从磁盘页、文件格式、B-Tree、LSM Tree、事务与崩溃恢复出发，说明数据如何被组织、更新和持久化；下半部分讨论故障检测、选主、复制、反熵、分布式事务与共识，说明多台不可靠机器如何协作成一个数据库。
  • 为什么（Why）：
    • 数据库提供的表、索引、事务和一致性都是昂贵抽象。其真实行为受存储介质、页布局、缓存命中率、写放大、网络延迟、节点故障和协议假设共同约束。只有理解这些约束，才能解释为什么同一条查询在不同负载下差异巨大，为什么已经返回成功的写入仍可能丢失，以及为什么高可用、一致性和低延迟不能无条件兼得。
  • 怎么做（How）：
    • 分析数据库时沿两条路径追踪：单机上追踪一次写入经过内存、WAL、数据页和后台维护的过程；分布式环境中追踪一次操作经过路由、复制、确认、故障切换和修复的过程。先明确负载与正确性目标，再比较读、写、空间和网络放大，最后结合故障模型选择结构与协议。不要只凭“B-Tree 读快、LSM 写快”或“用了多数派所以强一致”之类标签做判断。

核心观点：

数据库不是某一种数据结构或算法，而是一组相互约束的子系统：存储结构决定数据怎样落盘，事务和恢复机制决定更新怎样安全生效，分布式协议决定副本怎样形成共同历史。每层都在利用批处理、缓存、间接寻址、不可变性和冗余，把昂贵的随机 I/O、同步等待和故障恢复移出前台路径；代价则以读放大、写放大、空间放大、维护流量和更复杂的状态机重新出现。

全书可以压缩成三个问题：

  1. 数据怎样布局？ 数据库以页和记录为基本单位，在 B-Tree 或 LSM 等结构中组织数据，以减少设备 I/O 并支持目标访问模式。
  2. 更新怎样可靠？ 数据页更新不是原子的，需要 WAL、缓冲池、并发控制和恢复算法共同保证原子性、持久性与隔离性。
  3. 副本怎样一致？ 节点只能通过有延迟且可能失败的网络交换局部知识，需要复制、故障检测、选主、反熵、原子提交和共识协议管理分歧。

第一部分：存储引擎

1. 从工作负载和介质约束出发

数据库首先要在访问模式和硬件特征之间做匹配：

  • 事务型负载（OLTP）：大量短事务、点查和小范围更新，关心单次请求延迟与并发。
  • 分析型负载（OLAP）：扫描大量记录并聚合少数字段，关心顺序吞吐、压缩率和向量化处理。
  • 行式存储适合读取或更新完整记录；列式存储适合只扫描少数字段并按列压缩。
  • 磁盘和 SSD 都更擅长较大块的顺序 I/O，而不是许多细碎随机 I/O；内存虽快，却不是无限且默认持久的。

因此，数据库不会直接为每条记录单独访问磁盘，而是以固定大小的**页（page）**作为读写、缓存、校验和恢复的基本单位。一次逻辑记录更新，最终会变成对一个或多个页的修改。

存储引擎要同时管理三类放大：

指标 含义 常见来源
读放大 为返回一份数据额外读取了多少页、文件或副本 多层索引、多个 SSTable、缓存未命中
写放大 一次逻辑写导致数据被写入或重写多少次 WAL、页分裂、compaction、复制
空间放大 保存逻辑数据之外额外占用多少空间 空洞、旧版本、墓碑、冗余副本

这三者往往无法同时最小化。一个结构减少前台随机写，通常会把成本转移到读取、空间占用或后台整理。

2. 页和文件格式：数据结构必须可持久化

内存里的指针在进程重启后没有意义，磁盘结构需要稳定的二进制布局和可解析的引用。一个页通常包含：

  • 页头：页类型、记录数、空闲空间边界、校验和、版本等元数据。
  • 槽目录（slot directory）：保存单元格的偏移和长度，让记录可在页内移动而不改变外部引用。
  • 单元格（cell）：键、值或指向子页/溢出页的引用。
  • 空闲空间：供插入、更新和页内整理使用。

槽页解决了变长记录带来的间接寻址问题：外部可以引用“页号 + 槽号”，页内整理时只更新槽目录，不必修改所有索引指针。超出页容量的大值则可拆到 overflow page，但额外跳转会增加读取成本。

文件格式设计还要考虑：

  • 字节序、定长与变长编码；
  • 版本兼容与格式升级；
  • 校验和，以识别静默数据损坏或 torn page；
  • 页内碎片和可用空间管理；
  • 解析边界，避免损坏长度字段扩散成越界读取。

关键认识：磁盘数据结构不仅要支持查询，还要在任意时刻都能被验证、恢复和演进。

3. B-Tree：用宽而矮的有序树减少 I/O

B-Tree 把许多有序键放在同一个页中，使每个节点拥有较高扇出，从而让树保持很矮。内部节点保存分隔键和子页引用，叶子节点保存记录或记录位置；从根到叶的路径长度就是一次查找所需的主要随机 I/O 次数。

核心不变量包括：

  • 节点内键有序，子树的键范围由分隔键界定；
  • 除根节点外，节点占用率有下限和上限；
  • 所有叶子位于同一深度；
  • 插入导致溢出时分裂节点，并把分隔键向父节点传播；
  • 删除导致占用不足时，从兄弟节点借位或合并，并更新父节点。

B+Tree 常把真正的数据保存在叶子，内部节点只负责导航；叶子间通过 sibling link 相连，可高效执行范围扫描。

实现细节比抽象算法更重要

教科书里的 B-Tree 操作通常假设单步原子修改，但真实数据库需要处理：

  • 一个逻辑操作可能修改叶子、父节点甚至一路传播到根；
  • 并发线程可能同时搜索、分裂和合并同一条路径；
  • 进程可能在任意两个页写入之间崩溃；
  • 更新和删除会留下不可直接复用的碎片；
  • 单调递增键可能持续命中最右侧页，形成并发热点。

数据库会使用 latch 保护内存页结构，并通过 latch crabbing、sibling link、high key 等技术缩小锁定范围，使读者在结构变化期间仍能导航到正确页。页分裂的正确性不仅取决于“键是否分成两半”，还取决于链接和父指针以什么顺序发布。

B-Tree 的维护成本

  • 随机更新会原地改页，并产生 WAL 和脏页回写。
  • 页分裂可能造成额外 I/O，低填充率会带来空间放大。
  • 删除记录后，空间不一定立刻归还，需要 vacuum、页合并或碎片整理。
  • 批量加载已排序数据，可以自底向上构造页面，避免逐条插入和重复分裂。
  • 前缀压缩可以减少内部节点中重复键的存储，提高扇出并降低树高。

4. 事务处理：逻辑原子性建立在非原子的页写之上

事务通常用 ACID 描述，但四个属性由不同机制共同实现：

属性 要解决的问题 典型机制
Atomicity 事务不能只执行一半 undo、版本、原子提交协议
Consistency 事务前后业务不变量成立 数据约束 + 应用逻辑 + 原子性/隔离性
Isolation 并发事务不应观察到非法中间状态 锁、时间戳、MVCC、串行化验证
Durability 已提交结果在故障后仍存在 WAL、fsync、复制、恢复

这里的 Consistency 是应用不变量，不等于分布式系统里的副本一致性模型；数据库只能提供执行机制，无法自动证明所有业务规则。

Buffer Pool

数据库通过缓冲池缓存热页，避免每次访问磁盘：

  • 读页时先查 page cache；未命中才从磁盘装入 frame。
  • 更新通常先修改内存中的页并标记 dirty，不必同步写回数据文件。
  • 淘汰算法既要考虑最近/频繁访问，也要避免扫描污染整个缓存。
  • 正在被使用或尚不能安全落盘的页需要 pin，不能随意淘汰。

缓冲池让性能显著提高，也带来一个恢复难题：提交时数据页可能尚未写盘；未提交事务修改过的脏页又可能先被淘汰到磁盘。

Write-Ahead Log

WAL 的核心规则是：描述修改的日志必须先于对应数据页持久化。事务返回提交成功前，还必须让它的 commit record 达到持久存储。

典型写路径如下：

  1. 在内存中生成日志记录，为其分配递增的 LSN。
  2. 修改缓冲池中的目标页，并把页标记为 dirty。
  3. 提交时把该事务截至 commit record 的 WAL 刷盘。
  4. 数据页稍后由后台线程批量写回，写回前确认相关 WAL 已经持久化。

WAL 把大量细小随机页写转换为追加日志，再允许数据页乱序、批量回写。一次 fsync 还可以为多个事务共同完成持久化，即 group commit。

崩溃恢复

恢复算法必须区分：哪些事务已提交但数据页尚未落盘，需要 redo；哪些事务未提交但修改已经写入数据文件，需要 undo。

以 ARIES 思路概括：

  1. Analysis：从 checkpoint 附近重建崩溃时的脏页表和活跃事务表。
  2. Redo：重复历史，把可能未落盘的修改恢复到崩溃前状态；page LSN 可避免重复执行已存在的更新。
  3. Undo：按相反方向撤销未提交事务，并写 compensation log record，让恢复过程本身也可再次恢复。

Checkpoint 不是把数据库“暂停并全部写干净”，而是缩小恢复时需要扫描的日志范围。正常运行的吞吐与故障后的恢复时间之间仍需权衡。

5. B-Tree 变体：围绕写入和并发重新安排工作

经典 B-Tree 不是终点。不同变体通过改变修改传播方式来优化特定瓶颈：

  • Copy-on-Write B-Tree：不覆盖旧页，而是创建新页并一路复制到根；提交可归结为切换根指针，天然保留快照，但随机更新可能复制整条路径。
  • Bw-Tree：借助映射表和 delta record 避免原地修改页面，以 CAS 发布变化，再由后台 consolidation 合并增量；降低 latch 依赖，但读取要遍历增量链。
  • Fractal Tree / FD-Tree：在内部节点缓冲更新，攒成批后向下传播，把随机写转化为批量顺序工作；代价是读取和维护逻辑更复杂。
  • Cache-oblivious B-Tree：不显式固定块大小，通过递归布局尝试在不同缓存层级获得局部性。

这些设计都在回答同一个问题：能否延迟、批量或间接发布修改，从而减少前台随机写和结构锁竞争。它们没有消灭工作，只是改变了工作发生的时间和位置。

6. LSM Tree：前台追加，后台归并

LSM Tree 把随机更新先写入内存有序结构，再按不可变文件顺序落盘：

写入路径

  1. 追加 WAL，保证 memtable 丢失后可以恢复。
  2. 更新内存中的有序 memtable。
  3. memtable 达到阈值后冻结为 immutable memtable，并顺序写成 SSTable。
  4. 后台 compaction 归并文件、保留新版本并清理安全可删除的旧版本与墓碑。

SSTable 内部按键有序，通常配有稀疏索引、数据块索引和 Bloom filter。Bloom filter 能快速证明“某文件一定没有这个键”，但不能证明键一定存在，并且只优化点查而非任意范围扫描。

读取路径

读取需要从新到旧检查 memtable 和可能覆盖目标键范围的 SSTable，找到最新可见版本。文件和层级越多，读放大越高；block cache、Bloom filter、索引和 compaction 都是在减少实际查询的文件数。

删除通常写入 tombstone，因为旧值可能仍存在于更老文件中。只有当 compaction 能确认不会让旧版本“复活”，且不再受快照、复制或修复窗口约束时，墓碑才能被安全清理。

Compaction 策略

策略 做法 典型权衡
Size-tiered 把大小相近的文件成批合并 写入成本较低，但重叠文件多，读和空间放大较高
Leveled 每层控制大小，除 L0 外尽量让键范围不重叠 读和空间放大较低，但数据可能在层间被反复重写

Compaction 是 LSM 的代价结算器：它消除旧版本、回收墓碑、降低读放大，却消耗磁盘带宽和 CPU，并可能与前台请求争抢资源。若写入速度持续超过 compaction 能力，就会形成 compaction debt，最终表现为文件数增长、空间膨胀和延迟尖峰。

B-Tree 与 LSM 的正确比较方式

维度 B-Tree 家族 LSM 家族
当前视图 原地维护一个主要有序结构 多个按时间形成的有序结构共同构成当前视图
前台写入 更新页，可能触发分裂和随机 I/O WAL + memtable，主要为追加与内存更新
点查 路径稳定，通常检查单棵树 可能检查多层文件，依赖过滤器和缓存
范围扫描 叶子连续，行为较直观 需要多路归并并处理版本与墓碑
后台工作 刷脏页、vacuum、页合并 flush、compaction、墓碑回收
主要风险 随机写、页碎片、结构热点 compaction 抢占、读放大、空间暂增

不能脱离以下因素宣布谁“更快”：读写比例、键分布、值大小、范围查询比例、缓存容量、设备特性、压缩率、持久性设置和尾延迟目标。

第二部分：分布式系统

7. 分布式系统的基本约束

单机数据库可以依赖本地函数调用、共享内存和相对清晰的失败边界；分布式数据库面对的是局部知识：

  • 消息可能延迟、丢失、重复或乱序；
  • 节点可能暂停、崩溃、重启，磁盘也可能损坏；
  • 节点没有完美同步的全局时钟；
  • 超时不能证明远端失败，只能说明本地尚未收到响应；
  • 客户端重试时，无法仅凭超时判断前一次操作是否已经生效。

所以网络请求必须考虑唯一请求标识、幂等、去重和重试边界；协议必须明确系统模型和故障模型，不能把“通常很快”当作安全性前提。

8. 故障检测：超时输出的是怀疑

节点通常通过心跳和超时判断同伴是否可达：

  • 超时短，发现故障更快，但慢节点和网络抖动会制造误判。
  • 超时长，误判更少，但故障恢复和选主更慢。
  • 自适应检测器根据历史到达间隔估算怀疑程度，而不是只输出布尔值。

故障检测器的输出只能作为协议输入，不能单独授予节点成为 leader 的权力。否则两个互相不可达的节点都可能认为对方已死，形成 split brain。真正的排他性通常来自 quorum、epoch/term 和 fencing token。

9. Leader Election：选出 leader 还不够

选主需要同时保证：

  • 同一有效任期内不会有两个都能提交写入的 leader；
  • 新 leader 包含足够新的已提交历史；
  • 旧 leader 恢复或网络恢复后，不能继续以旧身份修改共享资源；
  • 系统稳定后能完成选举并继续服务。

任期号或 epoch 用来区分新旧领导权。外部存储也必须检查 fencing token，否则旧 leader 即使失去集群多数票，仍可能在暂停恢复后继续写入。

10. 复制与一致性：副本数量不等于正确性

复制可以提高容错、读吞吐并缩短地理距离，但会带来副本延迟和冲突。

  • 同步复制等待一个或多个副本确认后返回，故障时数据保证更强，但延迟和不可用风险更高。
  • 异步复制由主节点先返回，再传播更新，延迟较低，但主节点在复制前故障会产生已确认写入丢失窗口。
  • 单主复制集中排序写入，模型简单，但 leader 是写路径瓶颈和故障切换焦点。
  • 多主或无主复制允许多个位置接收更新，提高局部可用性，却必须检测和解决并发版本。

若系统有 N 个副本、写等待 W 个确认、读查询 R 个副本，R + W > N 只说明读写集合必有交集。它并不会自动得到线性一致性：还需要版本排序、并发写处理、读取最新值、节点成员视图和故障恢复等条件。

一致性必须用可观察行为描述，例如线性一致性、顺序一致性、因果一致性、读己之写或单调读；“强一致”和“最终一致”常常不足以成为可验证的契约。

11. 反熵与信息传播：修复副本分歧

即使正常写路径会复制，短暂离线、丢包和故障恢复仍会让副本缺少更新。系统需要后台机制持续发现和修复差异：

  • Read repair：读取多个副本时顺便修复旧版本。
  • Hinted handoff：目标副本不可用时暂存提示，恢复后补发。
  • Merkle tree：分层比较哈希，只传输不同的范围，避免逐条校验全部数据。
  • Gossip：节点周期性随机交换成员和状态摘要，让信息以概率方式扩散。

这些机制通常只保证最终传播，不天然提供操作全序。版本向量等逻辑时钟可以区分“一个版本覆盖另一个”和“两个版本并发”，但冲突最终仍需由确定性合并规则或业务语义解决。

12. 分布式事务：原子提交与共识不是一回事

跨节点事务首先要保证所有参与者共同提交或共同回滚。两阶段提交（2PC）分两轮完成：

  1. Prepare：协调者询问参与者能否提交；参与者持久化准备状态并锁定相关资源。
  2. Commit/Abort：全体同意才提交，否则回滚。

参与者一旦回答 prepared，就不能自行决定结果；如果此时协调者失联，它可能长期阻塞并持有资源。2PC 解决原子提交，但经典形式不容忍协调者不可达，因此不等于共识。

实践中要区分三个层次：

  • 本地并发控制决定每个分片内哪些操作可以并发执行；
  • 原子提交决定一个跨分片事务是否整体生效；
  • 共识复制保证每个参与角色及其决策在节点故障后仍可恢复。

把协调者和参与者状态复制到共识组，可以提高可用性，但没有消除跨分片协调、长尾等待和锁持有成本。

13. 共识：用多数派交集保护唯一历史

共识要求多个节点对同一个值或日志前缀达成决定。Paxos、Raft、ZAB 等协议表达方式不同，但都依赖相似基础：

  • 2f + 1 个投票节点最多容忍 f 个节点失效；
  • 任意两个多数派必有交集，已提交历史会被后续多数派中的至少一个节点携带；
  • 递增 term/ballot/epoch 区分新旧提案和领导权；
  • 投票与日志等关键状态必须持久化，重启不能忘记承诺；
  • 少数派必须停止决定新值，以安全性换取网络分区期间的部分不可用。

共识的首要目标是 safety：不能形成两个都被提交的冲突历史。网络持续不稳定时，系统可以暂时没有进展，但不能通过两个 leader 各自提交来制造“可用性”。成员变更、日志截断、快照安装和持久化边界，都是实现中与算法核心同样重要的正确性部分。

统一分析框架

面对一个数据库或存储系统，可以按以下顺序拆解：

1. 先问工作负载

  • 点查、范围扫描还是全表聚合？
  • 读多、写多还是突发写入？
  • 键和值多大，键分布是否单调或倾斜？
  • 更关注平均吞吐还是 P99/P999 延迟？

2. 再追踪单机写路径

  • 写入何时进入 WAL，何时真正持久化？
  • 数据页是原地更新还是生成不可变文件？
  • 提交是否依赖 fsync，是否做 group commit？
  • 崩溃后 redo/undo 从哪里开始，checkpoint 有什么保证？
  • 后台 flush、vacuum 或 compaction 是否会抢占前台资源？

3. 再追踪分布式确认路径

  • 请求由谁排序和提交，需要几个副本确认？
  • 返回成功时，哪些故障仍可能丢失结果？
  • leader 如何选举，旧 leader 如何被 fencing？
  • 客户端超时重试会不会重复执行？
  • 离线副本如何追赶，冲突版本如何合并？

4. 最后核对契约

  • 系统承诺哪一种隔离级别和一致性模型？
  • 保证在什么故障模型、持久化配置和副本配置下成立？
  • 备份能否恢复，恢复点和恢复时间目标是什么？
  • 性能收益是消灭了成本，还是把成本延迟到后台或故障期间？

启发点（关键洞察）：

  1. 数据库的大部分优化都在重新安排工作。 缓存把磁盘读取延后，WAL 把随机写改成追加，LSM 把整理移到 compaction，复制把恢复能力换成网络和一致性成本。评估优化时必须找到被转移的代价。
  2. 页是存储引擎真正的原子词汇。 表、行和索引是逻辑概念，而空间管理、缓存、校验、锁存和恢复最终都围绕页展开。
  3. 不可变性降低了原地协调，却增加了版本管理。 SSTable、copy-on-write、快照和追加日志更容易并发读取与恢复，但必须处理旧版本、墓碑、回收和空间放大。
  4. WAL 的价值不只是备份。 它通过明确写入顺序，把提交延迟与数据页回写解耦，是 steal/no-force 缓冲策略能够成立的基础。
  5. B-Tree 和 LSM 不是简单的“读优化/写优化”二选一。 两者都有 WAL、缓存和后台维护；真实结果取决于放大系数、设备、负载、压缩和延迟目标。
  6. 后台任务也是核心数据路径。 Compaction、vacuum、checkpoint 和 replica repair 若跟不上，前台短暂的高吞吐只是积累债务。
  7. 超时代表未知，不代表失败。 这直接推出客户端请求要有幂等语义或去重标识，也推出故障检测不能单独解决 split brain。
  8. 复制保存多个副本，共识保存一个决定。 有副本不代表它们同样新，也不代表故障切换后不会产生冲突历史。
  9. Quorum 交集是必要条件，不是完整一致性证明。 还必须追问版本、顺序、并发写、成员变更和读取规则。
  10. 原子提交、复制与共识解决不同问题。 2PC 决定多个参与者是否一起提交，共识让某个参与者的决策状态在故障后保持唯一；二者可以组合，但不能互相替代。
  11. 数据库正确性是一条端到端链路。 应用约束、事务隔离、WAL 持久化、存储校验、复制确认和故障切换任一环节的弱保证，都可能成为最终的数据安全边界。
  12. 性能测试必须覆盖稳态和恢复态。 空库基准或短时压测看不到缓存淘汰、compaction debt、墓碑堆积、故障追赶和 checkpoint 恢复成本。

行动：

  1. 以后评估数据库选型时，先记录工作负载、数据规模、正确性契约和故障模型，再讨论产品和数据结构。
  2. 为关键数据库画出完整写路径：client → WAL → memtable/buffer pool → data file → replica → acknowledgement，并标注每一步的持久化和失败语义。
  3. 监控不只看 QPS 和平均延迟，同时观察 cache hit、WAL fsync、dirty page、compaction backlog、读写/空间放大、replication lag 与恢复时间。
  4. 为所有可能超时重试的写操作设计 idempotency key、去重表或可安全覆盖的状态转移，不把网络错误直接等同于操作未执行。
  5. 压测 LSM 系统时持续运行到 compaction 进入稳态，并加入覆盖范围删除、墓碑回收和磁盘接近容量上限的场景。
  6. 做高可用演练时验证真实故障边界：leader 在确认前后崩溃、旧 leader 暂停后恢复、少数派隔离、磁盘写满、落后副本追赶和整集群重启。
  7. 阅读数据库文档时，把“强一致”“同步复制”“零数据丢失”等宣传语改写成可验证条件：等待哪些副本、何时 fsync、容忍哪些故障、少数派怎样处理。

金句：

  1. 数据库的抽象越简单，底层为维持这个抽象付出的协调成本往往越高。
  2. WAL 先记录意图，数据页随后兑现；恢复就是在故障后完成或撤销这些意图。
  3. B-Tree 持续维护一个有序视图，LSM 则让多个有序历史在后台逐步收敛成当前视图。
  4. 不可变文件让写入和恢复更简单，却把删除变成了一个需要证明安全后才能完成的过程。
  5. 超时之后得到的不是失败，而是未知；可靠系统必须设计如何处理未知。
  6. 复制解决“还有副本”，共识解决“哪份历史算数”。
  7. 性能优化没有消灭成本，只是把成本从前台挪到后台、从单次请求摊到批次，或从正常路径推迟到恢复路径。
