Concurrency

CSLang

并发是一种程序结构：在有限资源下，让多个任务安全地交错推进。

并发不等于并行，也不等于异步。

关于异步等待语义和 async/await 的实现方式，参见 asynchrony。

什么是并发

并发（concurrency）关注的是：

  • 系统中有多个需要推进的任务；
  • 这些任务的步骤可以交错执行；
  • 程序需要定义任务如何协作、通信、取消、等待和收尾。

因此，并发首先是程序结构问题，而不是硬件问题。即使只有一个 CPU 核心，多个任务也可以通过交错执行形成并发。

并发、并行与异步

  • 并发：多个任务在同一时间段内推进，步骤可以交错执行。
  • 并行：多个任务在同一时刻于不同 CPU 核心或执行单元上运行。
  • 异步：发起操作后不阻塞当前控制流，等待结果就绪后再继续执行。

可以这样区分：

  • 并发回答“如何组织多个任务”；
  • 并行回答“多个任务是否真的同时运行”；
  • 异步回答“等待结果时控制流如何继续”。

例如，单线程事件循环通常同时具备异步和并发结构；多线程阻塞式服务器可以并发处理请求，但不一定使用 async/await。

并发为什么困难

并发的难点不在于同时启动多个任务，而在于任务交错时仍然保持正确性。

典型问题包括：

  • 竞态条件（race condition）：结果依赖不可预测的执行顺序；
  • 数据竞争（data race）：多个执行流并发访问同一内存位置，至少一个是写操作，且没有同步；
  • 原子性破坏：x = x + 1 不是不可分割的操作；
  • 可见性与顺序问题：一个执行流的写入未必按预期被另一个执行流观察到；
  • 死锁（deadlock）：多个执行流互相等待，系统无法继续；
  • 活锁（livelock）：执行流持续活动，但没有实际进展；
  • 饥饿（starvation）：某个任务长期无法获得资源；
  • 背压缺失：生产速度大于消费速度，队列无限增长；
  • 取消与清理困难：任务无法停止，或资源无法完整回收。

并发缺陷通常低概率、依赖时序且难以复现，因此需要在设计阶段明确约束，而不能只依赖测试发现问题。

并发系统中的核心对象

任务

任务是逻辑上的工作单元，例如处理请求、同步数据、刷新缓存或计算结果。

执行体

执行体是承载任务的运行机制，例如：

  • OS thread；
  • goroutine；
  • coroutine / fiber；
  • 事件循环中的回调或任务。

不要把任务和线程绑定。好的并发模型通常允许任务数量远大于线程数量，并让等待中的任务释放执行体。

共享资源

多个任务可能共享内存对象、文件句柄、socket、数据库连接池、CPU 时间、锁和队列。

并发控制需要明确：

  • 谁可以访问资源；
  • 什么时候可以访问；
  • 访问顺序是什么；
  • 访问失败或任务取消后如何收尾。

常见并发模型

共享内存与锁

多个线程共享同一地址空间，通过锁保护临界区。

**优点：**直观，适合需要直接操作共享内存的低延迟组件。

**风险：**容易出现锁顺序问题、死锁、锁竞争和伪共享，正确性依赖同步纪律。

适合多核 CPU 密集型任务，或必须共享内存结构的场景。

消息传递

任务之间尽量不共享可变状态，而是通过消息通信，例如 Go channel、actor model 和 CSP 风格模型。

**优点：**降低共享状态的复杂度，使所有权和边界更清晰。

**风险：**复制、序列化和排队会带来开销；不合理的队列设计仍然会导致阻塞、堆积或泄漏。

适合服务内部流水线、worker pool 和状态边界明确的组件。

事件循环

一个或少量线程负责监听 I/O；当操作就绪时，调度对应任务继续执行。

**优点：**用少量线程处理大量 I/O 连接。

**风险：**CPU 密集任务或阻塞调用会长时间占用事件循环；调用栈和阻塞点也更难调试。

适合网络服务器、GUI 和高并发 I/O 系统。

结构化并发

将并发任务纳入明确的父子生命周期：

  • 谁创建，谁负责等待；
  • 子任务失败时如何传播；
  • 取消时是否整体退出；
  • 资源如何在作用域结束时回收。

结构化并发解决的是“任务启动了，却没有人负责收尾”的问题。相关关键词包括 scope、cancellation、join、timeout 和 error propagation。

同步原语

同步原语用于约束执行流访问共享状态的顺序和数量。

原语 解决的问题 核心抽象
Lock / mutex 同一时间只允许一个执行流访问临界区 互斥与所有权
Condition variable 条件不满足时等待，满足时唤醒 状态变化
Semaphore 限制同时使用资源的数量 资源计数
Atomic 对单个变量执行不可分割的操作 原子性
Barrier 等待所有参与者到达某个阶段 阶段同步
Channel / queue 通过通信传递数据并协调执行 消息与同步

常见原则：

  • 能缩小共享状态，就不要扩大锁的范围；
  • 能通过所有权转移解决，就少使用共享可变内存；
  • 能用高层抽象表达，就不要过早使用裸 atomic；
  • 锁和条件变量应保护明确的不变量，而不是只保护某一行代码。

性能取舍

并发的目标不是简单地增加线程数量。需要同时考虑：

  • 吞吐量：单位时间完成的工作量；
  • 延迟：单个任务完成所需的时间；
  • 资源占用：线程、内存和连接数；
  • 公平性：是否有任务长期得不到资源；
  • 可预测性：高负载下是否平滑退化。

常见误区包括：

  • 线程过多导致上下文切换开销增加；
  • 锁竞争使 CPU 时间消耗在等待上；
  • 队列过深导致延迟上升；
  • 任务过细导致调度成本超过计算本身；
  • 缓存一致性流量和伪共享拖慢多核程序。

设计并发程序时先问什么

  1. 任务边界是什么？
  2. 哪些数据是共享的？哪些可以变成私有的？
  3. 正确性依赖哪些顺序保证？
  4. 失败和取消如何传播？
  5. 谁负责等待子任务结束？
  6. 是否需要背压？队列上限是多少？
  7. 这是 I/O 密集型还是 CPU 密集型任务？
  8. 能否把并发限制在少数明确的组件中？

先设计所有权，再设计同步；先减少共享，再考虑如何加锁。

工程实践

优先避免共享可变状态

优先级通常是：

  1. 不共享；
  2. 只读共享；
  3. 转移所有权；
  4. 不得不共享时再添加同步。

明确任务生命周期

每个后台任务都应明确：

  • 什么时候启动；
  • 什么时候退出；
  • 谁负责取消；
  • 谁负责等待和回收。

限制并发度

“能并发”不代表“应该无限并发”。常见手段包括 worker pool、semaphore、bounded queue 和 rate limit。

把取消作为一等公民

超时、用户离开、上游失败和服务关闭都可能触发取消。取消路径设计不完整时，容易出现资源泄漏和悬挂任务。

建立可观测性

至少应关注队列长度、锁等待时间、线程或 goroutine 数量、超时率、取消率、吞吐量和尾延迟。

心智模型

可以用以下模型理解大多数并发系统：

  • 系统中有多个任务；
  • 任务需要执行体才能推进；
  • 某些步骤需要等待外部事件；
  • 某些步骤需要访问共享资源；
  • 同步原语约束访问顺序；
  • 调度器决定谁先运行；
  • 取消、超时和错误传播决定系统如何收尾。

如果这些元素都能画清楚，并发系统通常就能被解释、设计和验证。
