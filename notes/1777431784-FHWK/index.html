读书笔记：Is Parallel Programming Hard

2026-04-292026-07-28
BN

并行编程的核心不是多开线程，而是管理共享状态：尽量少共享；必须共享时，明确所有权、同步边界、可见性顺序和性能成本。

  • 是什么（What）：
    • 一本面向工程实践的并行程序设计方法论：它不只罗列并发原语，而是从硬件行为出发，讨论如何拆分工作与资源、控制共享访问、回收并发对象，并验证正确性与可扩展性。
    • 全书以 Linux 内核经验和 RCU 为重要案例，但核心原则也适用于数据库、服务端和其他共享内存系统。
  • 为什么（Why）：
    • 多核让并行成为常态，但共享状态会同时带来竞态、死锁、内存序错误和扩展性瓶颈；程序即使逻辑正确，也可能因为缓存争用和全局序列化而无法扩展。
    • 源码顺序不等于实际执行顺序，缓存一致性也不等于业务一致性。只凭顺序程序的直觉，无法可靠地推断并发程序。
    • 性能、生产率和通用性彼此制约，不存在适合所有负载的同步方案；需要一套根据业务语义和访问模式做取舍的方法。
  • 怎么做（How）：
    1. 先定义语义：结果必须精确还是允许近似，是否允许重试、阻塞或延迟回收。
    2. 再减少共享：优先分区、复制、局部缓存和明确所有权，把全局热点拆成局部状态。
    3. 刻画访问模式：识别读写比例、争用强度、快慢路径以及数据生命周期。
    4. 选择最简单且满足语义的机制：能用所有权就不共享，能用锁就不贸然 lock-free；读多写少且允许延迟回收时，再考虑 RCU 等专门方案。
    5. 明确正确性边界：为共享数据定义不变量、同步关系、内存顺序和对象回收时机。
    6. 用测试、断言、跟踪、模型检查、基准测试和性能分析共同验证，并根据证据迭代设计。

核心观点：

  1. 全书给出了一条递进的方法链：先理解硬件，再掌握基本工具；继而通过计数、分区、锁、所有权、延迟处理和数据结构学习设计；最后用验证、形式化方法和内存模型保障正确性。高级并发技术建立在这条链上，不能绕过基础原则。
  2. 并行编程的目标不只有性能，还有 productivity 和 generality。三者经常冲突，因此并行设计本质上是在特定负载和约束下做取舍，而不是寻找银弹。
  3. 并行之所以难，主要难在：
    • 工作拆分 work partitioning
    • 并发访问控制 access control
    • 资源拆分与复制 resource partitioning/replication
    • 与硬件行为对齐 hardware interaction
    • 多种能力组合后的复杂性 composite capabilities
  4. 硬件是并行设计的约束而不是实现细节。编译器与 CPU 会重排序，cache miss、I/O、跨核缓存同步和原子操作都有成本；缓存一致性只能保证硬件层面的值传播，不能替程序建立业务不变量。很多竞态和性能崩坏，本质上是程序违背了硬件习性。
  5. 设计应从 partition first 开始。可以按数据、线程归属、快慢路径拆分，也可以使用层级锁和局部缓存。性能通常来自把热点拆散、减少争用和全局序列化，而不是让更多线程以更复杂的方式访问同一份状态。
  6. 明确的数据所有权是最强的简化手段之一。线程归属、消息传递、私有化和进程隔离，都能把“如何同步共享”转化为“谁有权修改”。
  7. 很多问题不是加锁就行，而是要先决定：
    • 数据归谁管
    • 读多写少还是写多读少
    • 是否允许延迟回收
    • 是否接受近似结果
  8. 锁不是落后技术，lock-free 也不天然更优。锁除了执行成本，还可能引入死锁、活锁、饥饿、不公平和扩展性问题；但在应用代码中，它往往仍是最容易验证的选择。线程、锁、读写锁、原子操作和线程/CPU 局部变量都只是工具，必须根据访问模式、争用程度、进展保证和团队验证能力选择，不能默认 mutex，也不能盲目追求无锁。
  9. 延迟处理把“更新”与“确认旧读者已经离开”分开，是解决并发对象生命周期的关键思路；内存回收往往比并发访问本身更难。引用计数直观但更新较重，Hazard pointers 适合无锁场景但使用复杂，SeqLock 让读路径较快但可能重试，RCU 则代表读多写少 + 延迟回收 + 降低读侧同步成本的设计思想。
  10. 精确性具有同步成本，计数器正是并发设计的缩影。统计型计数可以允许暂时不精确，近似限额以误差换速度，精确限额则必须为边界保证支付更高同步成本。应先确定所需语义，再决定是否值得进行全局协调。
  11. 数据结构决定并行能力的上限：可分区、可复制、读写路径可分离的结构更容易扩展；如果结构本身制造全局热点，微调锁通常无济于事。
  12. 并发验证的目标不是证明自己正确，而是系统地寻找反例。测试、断言、跟踪、静态分析、代码审查、litmus test、模型检查和基准分析需要相互补充。
  13. 内存顺序是 lock-free、RCU 等高级同步机制的正确性边界。重排序同时来自编译器和硬件，acquire、release、barrier、dependency、cache coherence 与 multicopy atomicity 都会影响可观察结果；不理解这些约束，代码即使偶然通过测试也不代表正确。
  14. 非阻塞同步、实时系统、事务内存和函数式并行等高级主题，不会替代分区、所有权、验证和内存序等基础原则；复杂同步技术的价值只能在明确的负载与约束中判断。

启发点（关键洞察）：

  1. 并行设计先问能不能少共享，再问怎么同步共享。
  2. 正确的数据所有权设计，价值常常高于花哨的 lock-free。
  3. 读多写少场景，RCU 是非常强的思路。
  4. 计数器不是小问题，而是并发设计缩影。
  5. 锁的问题主要不在慢，而在会形成全局串行点。
  6. 精确性是昂贵的，很多系统应该先争取足够正确。
  7. 缓存、一致性、内存序会决定并发代码真实行为。
  8. 数据结构决定上限，API 技巧只能做局部优化。
  9. 并发验证要靠多种手段叠加，不能迷信单一测试。
  10. 并行编程首先是工程 discipline，不是技巧表演。

行动：

  1. 以后遇到并发性能问题，先从是否能减少共享状态入手，而不是直接换锁。
  2. 设计计数器时，先明确它是统计型、近似限额型，还是精确限额型。
  3. 对读多写少的数据路径，优先考虑 RCU、只读快路径和延迟回收。
  4. 对高争用热点，优先考虑分片、局部缓存、线程所有权，而不是全局原子变量。
  5. 任何涉及 lock-free、内存屏障、对象回收的代码，都要配套验证策略。

金句：

  1. 这本书真正教的不是并发技巧，而是把共享内存并行问题，改写成硬件能承受、团队能验证、系统能扩展的工程结构。
