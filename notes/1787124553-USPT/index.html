核心结论

  1. 文件系统的本质是 namespace + metadata abstraction：它把匿名的块地址空间组织成可命名、可导航、可管理的数据空间。
  2. 共享文件系统的核心难题不是存储，而是协调：共享状态会把原本廉价的本地协调变成昂贵的远程协调。
  3. 常见的优化方法是 ownership + localization：先取得一片状态的独占处理权，再把高频操作尽量留在本地完成。

从块设备到文件系统

块设备提供的接口非常简单：给定第 N 个块，读取或写入固定大小的数据，例如 4 KB。它只提供匿名的 block address space，并不关心数据如何命名、归类和查找。

文件系统在块设备之上增加了一套数据组织结构，主要提供：

  • 文件与目录组成的命名空间；
  • 文件大小、权限、时间等元数据；
  • 从路径到数据块的映射；
  • 空间分配、回收和一致性管理。

因此，文件系统并不是另一种存储介质，而是对底层块存储的组织与管理抽象。

共享文件系统为什么慢

单机文件系统中的许多操作都依赖协调，例如检查权限、更新目录、加锁、修改元数据和保证读写一致性。这些操作在本地通常很便宜。

到了 NFS 等共享文件系统中，同样的协调需要跨网络完成。真正昂贵的往往不只是文件内容的传输，而是：

  • 每次元数据操作都可能产生网络往返；
  • 多个客户端需要共同维护缓存一致性；
  • 锁、并发写入和故障恢复都依赖分布式协调；
  • 小而频繁的操作难以通过吞吐量掩盖网络延迟。

所以，NFS 的主要瓶颈通常是 remote coordination，而不只是网络带宽。

Local Disk + S3 的职责分工

一种常见架构是让本地磁盘承担活跃工作集，让 S3 充当持久化后端：

Local Disk S3
hot data durable data
mutable state cheap storage
random access large-scale capacity
metadata-heavy operations shared data
working state long-term retention

这种设计把频繁、细粒度、需要低延迟协调的操作留在本地，只把较大粒度的数据持久化和共享交给对象存储。

它减少了远程协调，但引入了新的成本：本地磁盘与 S3 之间需要搬运数据。当工作集很大、节点频繁切换或数据局部性较差时，数据传输会成为新的瓶颈。

Distributed Ownership FS

进一步的思路是把数据划分为多个分片，并让某个节点在一段时间内拥有某个分片的处理权：

  1. 通过分布式协调确定分片的 owner；
  2. owner 把分片所需的数据和状态加载到本地；
  3. 分片内的大量读写、缓存和元数据操作在本地完成；
  4. 只有 ownership 变化、持久化或跨分片操作需要远程协调。

这相当于用少量、粗粒度的协调，换取大量、细粒度操作的本地化。其关键不变量是：同一时刻，一片需要互斥修改的状态只能有一个有效 owner。

架构演进

这条演进路线反复权衡三类成本：存储成本、数据搬运成本和协调成本。系统设计的重点不是消除所有成本，而是根据工作负载，把最频繁的操作放到成本最低的位置。
