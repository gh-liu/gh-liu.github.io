Q 用户态程序如何安全地请求内核服务？

A 应用按照系统调用 ABI 准备调用号和参数，再执行体系结构提供的陷入指令进入内核；内核入口保存状态、验证参数并分派具体服务，完成后恢复用户态执行。

1. 系统调用边界

系统调用是用户态进入内核态的受控入口。应用不能直接调用任意内核函数，只能通过内核公开的系统调用表请求服务，例如：

  • 进程：fork、execve、wait4、exit。
  • 文件：openat、read、write、close。
  • 内存：mmap、munmap、mprotect。
  • 网络：socket、connect、accept、sendto、recvfrom。

标准库通常会封装这些接口，但库函数和系统调用不是一一对应的：一个库函数可能完全在用户态完成，也可能组合多次系统调用。

2. 一次调用如何执行

简化流程如下：

  1. 用户态 wrapper 按 ABI 把系统调用号和参数放入约定位置。
  2. CPU 执行 syscall、svc 等指令，切换到预先配置的内核入口和特权级。
  3. 内核保存必要的用户态上下文，检查调用号、指针、长度、权限和资源状态。
  4. 内核执行具体服务，把结果或错误码写入 ABI 约定的位置。
  5. 返回指令恢复用户态特权级、程序计数器和寄存器状态。

用户指针不能被内核直接信任。内核必须检查地址范围和访问权限，并使用安全的用户内存访问机制；验证与实际访问也必须服从并发和缺页语义。

3. 系统调用、异常与中断

  • 系统调用（system call）：程序主动请求内核服务。
  • 异常（exception）：当前指令同步触发的事件，例如缺页、非法指令或除零。
  • 中断（interrupt）：通常由外部设备或定时器异步触发。

三者都可能让 CPU 进入内核，但触发源和处理语义不同。系统调用是一种有意设计的软件接口，不能把所有用户态到内核态的切换都称为系统调用。

4. 系统调用不等于上下文切换

系统调用一定涉及特权级切换，但不一定切换进程或线程。如果调用可以立即完成，内核可以直接返回原线程。

以下情况才可能触发任务切换：

  • 调用需要等待 I/O、锁或其他事件，当前线程进入睡眠。
  • 更高优先级任务就绪，当前任务被抢占。
  • 当前任务时间片耗尽或主动让出 CPU。

因此应区分：

  • mode switch：用户态与内核态之间切换。
  • context switch：保存一个任务并恢复另一个任务。

5. ABI 与平台差异

系统调用 ABI 由操作系统、CPU 架构和运行模式共同决定。例如：

  • 旧式 32 位 x86 Linux 常见 int 0x80。
  • x86-64 Linux 主要使用 syscall。
  • AArch64 Linux 使用 svc。

它们使用的调用号、参数寄存器和错误返回约定并不相同。阅读汇编时必须先确认目标平台，不能把某一种约定当成通用规则。

POSIX 规定的是源代码层面的可移植接口，不等同于某个内核的二进制系统调用 ABI。例如 POSIX open() 在 Linux libc 中可以由 openat 等实际系统调用实现。

6. 开销

系统调用的成本来自入口/出口、状态保存、安全检查以及可能的数据复制，但不能一概归因于上下文切换。实际成本还取决于：

  • 是否阻塞并触发调度。
  • 是否发生缺页或设备 I/O。
  • 是否复制大量数据。
  • CPU 安全缓解机制和内核实现。

批处理、共享内存和 io_uring 等机制可以减少调用次数或数据搬运，但也会增加协议、生命周期和并发控制复杂度。
