读书笔记：understanding distributed systems

2025-03-302026-07-30
BNSystem-design

从通信、协调、扩展、韧性和可维护性理解分布式系统

https://understandingdistributed.systems

  • 是什么（What）：
    • 一份连接分布式系统理论与大规模后端工程实践的全景指南
    • 以通信、协调、可扩展性、韧性和可维护性五条主线，解释云应用如何从单机演进为可扩展、可容错、可运营的分布式系统
  • 为什么（Why）：
    • 分布式系统的复杂性不是机器数量本身，而是远程通信存在延迟、部分失败和结果不确定性；扩容又会增加组件数量与故障概率
    • 理论材料往往缺少落地语境，实践材料又容易变成孤立的模式清单；需要一套从底层约束推导工程方案的认知框架
  • 怎么做（How）：
    • 从网络调用的真实成本出发，逐层理解发现、API、时间、复制、一致性和事务
    • 用功能拆分、数据分区、复制扩展系统，用冗余、隔离、限流、降载控制故障
    • 把测试、发布、监控、可观测性和可管理性当作系统能力，而不是上线后的附加工作

核心观点：

分布式系统设计的核心，不是消除故障，而是在通信不可靠、节点会失败、负载会变化的前提下，仍然向用户提供明确的语义和可接受的服务质量。

扩展性会增加活动部件，活动部件会增加故障概率。因此，每一次拆分、分区和复制，都必须同时回答如何隔离故障、观测退化和恢复服务。

一、通信：远程调用不是本地调用

  • 进程间通信是分布式系统的起点。一次 API 调用依赖 DNS、IP、TCP、TLS 和 HTTP 等多层协议；上层抽象会泄漏，排障时必须能沿协议栈向下追踪
  • IP 提供尽力而为的数据报，可能丢失、重复和乱序；TCP 在其上通过序列号、确认、重传、流量控制和拥塞控制提供可靠、有序的字节流
    • TCP 没有消息边界，应用必须自行分帧
    • TCP 确认只代表数据到达对端协议栈，不代表业务逻辑已经成功执行
    • 连接建立、慢启动、队头阻塞和重传都会体现在尾延迟上
  • TLS 在可靠链路上提供机密性、完整性和身份认证；加密并不自动解决证书信任、密钥轮换和端点授权问题
  • DNS 是一个分层、分布式、带缓存、最终一致的键值系统：TTL 降低查询压力，却使变更不能立即生效；不能把 DNS 更新当成瞬时、原子的流量切换
  • API 是服务之间的长期契约：
    • 接口应围绕资源和业务语义，而不是暴露内部数据结构
    • 请求需要验证、认证、授权和大小限制；错误应可分类，并给调用方足够的处理信息
    • 兼容性优先于整洁地重写；字段新增、废弃和版本迁移要允许新旧客户端并存
    • 远程写操作应定义超时、重试和幂等语义，不能假设一次调用恰好执行一次

二、协调：在不确定性中形成共同决定

  • 先明确系统模型，再讨论算法是否正确：
    • 节点可能崩溃、暂停或运行缓慢，网络可能延迟、丢包、重复、乱序和分区
    • 同步系统有已知时间上界，异步系统没有；现实通常按部分同步建模，即正常时期近似有界，但不能假设永远有界
    • 安全性描述坏事永远不发生，活性描述好事最终会发生；网络分区时，系统经常牺牲活性来守住安全性
  • 故障检测器提供的是怀疑而不是真相。心跳超时无法区分节点崩溃、网络中断、机器过载和长时间暂停；阈值太短会误判，太长会延迟恢复
  • 物理时钟会漂移、跳变且机器之间不同步：
    • 测量本机耗时使用单调时钟，不使用墙上时钟
    • Lamport 时钟表达事件的偏序约束，不能还原真实时间，也不能仅凭时间戳判断两个事件是否并发
    • 需要跨节点顺序时，应依靠协议形成顺序，而不是相信last-write-wins中的物理时间戳天然正确
  • 选举领导者不是得到最多票这么简单：旧领导者可能只是暂时失联，恢复后继续执行写操作
    • 租约必须考虑时钟与暂停
    • 使用单调递增的 term/epoch 和 fencing token，让资源端拒绝旧领导者的迟到请求
    • 领导权与数据新旧程度要一起判断，不能选出缺失已提交记录的节点
  • 复制用冗余提高可用性、读取能力和数据耐久性，但会引入副本延迟、冲突、选主和恢复问题：
    • 单主复制简化写入排序，但领导者是写路径上的协调点
    • 多主和无主复制提高多地写可用性，却需要明确冲突检测、合并和客户端可见语义
    • 写入何时算成功、读哪个副本、落后副本如何追赶，是一个完整复制协议不可缺少的部分
  • CAP 只讨论网络分区发生时一致性与可用性的取舍；PACELC 补充了正常情况下也存在延迟与一致性的权衡。二者都不是简单的数据库分类标签
  • 避免协调往往比优化协调更有效：
    • 若操作可交换、可结合或幂等，就可以降低对全局顺序的依赖
    • CRDT 通过受约束的数据类型使并发更新确定性合并，换取无需同步协调的强最终一致性
    • 因果一致性只约束有因果关系的事件顺序，允许真正并发的事件独立执行
    • 弱化一致性前必须从业务异常出发，确认乱序、旧读和冲突是否真的可接受
  • 分布式事务把多个参与者的变化变成一个原子结果：
    • 2PC 能协调原子提交，但协调者或参与者失败时可能阻塞；它没有消除失败，只是把处理失败的复杂性封装进协议
    • 长事务和跨服务流程常用 Saga 拆成一系列本地事务，通过补偿处理部分完成；它牺牲隔离性，补偿也不一定等价于撤销
    • Transactional Outbox 将业务状态和待发送事件写入同一数据库事务，再异步投递，避免数据库已提交但消息未发送的双写裂缝
    • 消费者仍需幂等，因为发布、传输和消费任一阶段都可能重试

三、可扩展性：拆分、分区和复制

扩展系统只有三种基本杠杆：按职责拆分功能，按键空间分区数据，复制功能或数据。缓存、CDN、负载均衡、微服务和消息系统都是这些杠杆的具体组合。

  • 扩容前先定义负载和服务目标：请求率、数据量、读写比、对象大小、热点分布，以及平均值和高分位延迟。没有目标的可扩展无法验证
  • 垂直扩展简单且应优先考虑，但存在物理和成本上限；水平扩展突破单机上限，同时引入路由、协调、数据分布和部分失效
  • HTTP 缓存和 CDN 把响应放到离用户更近的位置，减少源站负载和延迟：
    • Cache-Control定义可缓存性与新鲜度，ETag/条件请求用于重新验证
    • CDN 适合静态、公共、读多写少的内容；个性化和敏感响应必须正确设置缓存键与访问边界
    • 缓存失效、版本化 URL 和源站回源能力需要一起设计
  • 分区把数据和负载分散到节点：
    • 范围分区支持范围扫描，但顺序写容易形成热点
    • 哈希分区分布更均匀，却破坏相邻关系；一致性哈希可减少成员变化时的数据迁移
    • 分区键决定负载上限，应围绕访问模式、基数和热点选择
    • 重平衡期间需要限速并保留容量余量，否则为了恢复平衡本身可能压垮系统
  • 大文件适合交给对象存储，通过元数据与内容分离、分块、复制和校验获得容量与耐久性；应用服务器不应成为大文件数据面的中转瓶颈
  • 负载均衡可以发生在不同层：
    • DNS 能做粗粒度地理和容灾路由，但受缓存与 TTL 影响
    • L4 依据连接与地址转发，性能高；L7 理解 HTTP，可按路径、头部和权重做更细的路由
    • 负载均衡必须结合健康检查、连接排空和过载保护，不能继续向已失效或已过载实例分流
  • 数据存储扩展通常先复制读，再对写入或容量分片；每一步都会降低查询、约束和事务的自由度。NoSQL 的价值是针对明确访问模式提供可预测扩展，不是自动优于关系数据库
  • 缓存以空间和一致性复杂度换延迟与吞吐：
    • cache-aside 简单，但读取回填可能覆盖新值，删除与更新之间也有竞态
    • 热点 key、缓存击穿、穿透和雪崩会把问题集中放大到后端
    • TTL 应加入随机抖动；热点重建可使用请求合并或互斥；缓存失效时后端必须能受控降级
    • 先估算不用缓存是否真的不能满足目标，再决定是否承担双份状态
  • 微服务主要解决组织与独立演进问题，不是性能优化手段。服务边界不清时，拆分只会把本地调用变成不可靠网络调用，并带来跨服务数据一致性和运维成本
  • 控制面管理配置、拓扑和策略，数据面处理用户请求：控制面可以相对低吞吐、强一致，数据面应在控制面短暂不可用时继续使用最后已知的有效配置
  • 异步消息解耦生产者和消费者的可用时间与处理速率，但也会引入积压、重复、乱序和毒消息：
    • 明确 at-most-once / at-least-once 的投递语义
    • 用幂等键和去重实现业务效果，而不是轻信exactly-once标签
    • 监控队列年龄而不只是队列长度，因为年龄更直接反映用户等待时间
    • 设置重试上限、退避与死信处理，并为重放保留足够上下文

四、韧性：把失败限制在可承受范围

  • 可用性是系统整体属性。串联系统中，依赖越多，整体可用性通常越低；并行冗余只有在副本不会因相同原因同时失败时才有效
  • 常见故障不仅来自硬件，还包括错误配置、软件缺陷、依赖退化、证书过期、资源泄漏、流量突增和操作失误。设计应假设故障最终一定发生
  • 冗余不能解决相关故障：同一软件版本、同一电源、同一网络、同一区域和同一配置会形成共同故障域。副本应跨越与目标故障相匹配的隔离边界
  • 故障隔离的目标是缩小爆炸半径：
    • bulkhead 为租户、流量类别或依赖分配独立资源，避免一个拥塞点耗尽所有线程、连接和内存
    • shuffle sharding 为每个租户选择不同的小型节点子集，在保留共享资源效率的同时降低租户间重叠
    • cellular architecture 把系统拆成可独立运行的单元，让一次故障只影响部分用户，并允许逐单元发布与回滚
  • 保护下游依赖：
    • 每次远程调用都应有超时，端到端 deadline 要在调用链中向下传播；分层独立超时可能让总耗时失控
    • 重试只适用于暂时性错误和幂等操作，采用指数退避与随机抖动，并设置重试预算
    • 多层同时重试会指数放大流量，应选择一个负责重试的层
    • circuit breaker 在持续失败时快速拒绝，给依赖恢复空间；它是稳定机制，不是错误处理的替代品
    • 降级返回较旧、较少或非个性化的数据，前提是业务明确接受这种语义
  • 保护自身免受上游过载：
    • 限流控制某个调用方在时间窗口内的使用量，配额应对应成本与公平性
    • load shedding 在资源饱和前主动丢弃低优先级工作，通常比接收全部请求后一起超时更好
    • admission control 根据当前容量决定是否接纳新工作；有界队列避免等待任务无限占用内存
    • backpressure 把消费者的处理能力反馈给生产者，从源头减速，而不是把压力隐藏在不断增长的队列里

五、可维护性：让系统能够安全变化和快速恢复

  • 测试应分层建立信心：单元测试验证局部逻辑，集成测试验证真实边界，端到端测试验证少量关键旅程。越靠近端到端，速度越慢、定位越难，不应让测试金字塔倒置
  • 分布式系统测试应主动注入延迟、超时、重复、乱序、节点重启和依赖失败；只覆盖成功路径无法验证容错机制
  • 对共识、并发等关键算法，可用模型检查和形式化规约探索人工难以穷举的状态空间；它不能代替实现测试，但能在编码前暴露设计错误
  • 持续交付把小变更频繁送入生产：
    • 自动化构建、测试、制品和部署流程，保证同一个不可变制品逐环境晋级
    • rolling、blue-green 和 canary 发布控制风险；数据库和消息格式变更应遵循 expand-and-contract，支持新旧版本并存
    • 发布与功能启用解耦，使用 feature flag 渐进开放并保留快速关闭能力
  • 监控回答已知问题是否发生，可观测性帮助从输出推断未知内部状态：
    • metrics 适合聚合趋势和告警，logs 记录离散事件，traces 关联跨服务请求；三者通过 request/trace ID 连接
    • 使用结构化日志，记录决策所需上下文，但避免泄露凭据和个人数据
    • 高基数维度适合日志和追踪，不应无边界地放入指标标签
  • SLI 是用户可感知行为的量化指标，SLO 是目标，error budget 是允许不达标的额度：
    • 可用性、正确性、延迟、新鲜度和持久性都可能成为 SLI
    • 告警应围绕 SLO 消耗速度，而不是每个瞬时资源波动
    • SLO 不是越高越好；额外的9会显著增加成本，并限制发布速度
  • 可管理性意味着在不发布代码的情况下安全改变系统行为：动态配置、流量开关、容量调整和功能开关都要有校验、审计、分批生效、回滚与 last-known-good 配置

贯穿全书的设计方法

  • 先从单机和最简单架构开始，只在容量、可用性或团队边界出现真实约束时分布化
  • 对每个新组件同时写出：它解决什么瓶颈、引入什么状态、如何失败、如何观测、由谁恢复
  • 不只设计正常路径，也要设计请求已经执行但响应丢失、旧节点恢复、缓存全部失效、依赖变慢而非宕机和系统过载这些灰色状态
  • 分别控制平均性能、尾延迟和爆炸半径；大规模系统的用户体验常由最慢依赖与最坏故障域决定
  • 优先消除不必要的协调和共享状态；确实需要强语义时，再明确支付延迟、可用性和复杂度成本

启发点（关键洞察）：

  1. 网络调用成功不是一个单一事实：发送成功、对端收到、业务执行、状态持久化、响应收到是不同阶段，失败发生在哪一段决定了能否安全重试
  2. 扩展模式与韧性模式必须成对出现：服务拆分对应隔离和 deadline，分区对应重平衡和热点治理，复制对应故障域和一致性协议
  3. 缓存、队列和副本都在保存额外状态；它们提升性能或可用性的同时，也扩大了需要维护一致性和观测滞后的范围
  4. 系统最危险的状态往往不是彻底宕机，而是慢、旧、部分成功；超时、fencing、幂等和可观测性正是为这些不确定状态服务
  5. 重试是局部合理、全局危险的机制：没有退避、抖动、预算和层级约束的重试，会把一次依赖退化放大成级联故障
  6. 冗余的价值取决于故障独立性。两个位于同一故障域、运行同一错误配置的副本，不等于高可用
  7. 微服务首先是组织扩展方案；如果没有独立部署、所有权或容量隔离需求，模块化单体通常更简单、更可靠
  8. 控制面与数据面分离的关键收益，是把管理变化的复杂性从高吞吐请求路径移开，并允许数据面在控制面故障时继续服务
  9. 运维能力是架构的一部分：无法快速发现、定位、降级和回滚的系统，即使正常路径设计正确，也不是可靠系统
  10. 最好的分布式机制不是最多的机制，而是满足明确语义与 SLO 的最小组合

行动：

  1. 为每个远程接口写清超时、deadline、可重试错误、幂等键、去重期限和最大请求/响应大小
  2. 评审重试时画出完整调用链，确保只有合适的一层重试，并配置指数退避、抖动与重试预算
  3. 引入缓存前记录无缓存基线，定义失效策略，并演练缓存全空时后端能否通过限流和请求合并存活
  4. 选择分区键时用真实流量验证分布，检查单租户、单时间段和单 key 是否可能形成热点
  5. 为复制系统明确 RPO/RTO、确认写入条件、读一致性、故障切换、fencing 和副本修复流程
  6. 对每个关键依赖配置 deadline、并发上限和降级策略；让等待队列有界，并在饱和前降载
  7. 按故障域审计冗余，确认实例、机架、可用区、区域、软件版本和配置错误是否会相关失效
  8. 用 SLI/SLO 和 error budget 驱动告警与发布，不以 CPU、内存等单一资源指标代替用户体验
  9. 发布共享契约时使用 expand-and-contract 和 canary，保证数据库、事件和 API 的新旧版本能同时运行
  10. 在故障演练中覆盖慢依赖、响应丢失、消息重复、节点长暂停、配置错误和恢复后的旧节点，而不只测试进程崩溃

金句：

  1. 分布式系统的可靠性，不来自假设组件不会失败，而来自限制失败的影响并自动恢复。
  2. 超时只能终止等待，不能证明远端操作没有发生。
  3. 每个缓存都在用一致性复杂度购买延迟，每个队列都在用时间和积压购买解耦。
  4. 冗余只有跨越了真正的故障域，才会转化为可用性。
  5. 重试会放大负载；系统最需要恢复空间的时候，恰恰最承受不起无节制的重试。
  6. 可扩展性解决系统如何增长，韧性解决增长后的系统如何失败。
  7. 微服务不是目的，而是在组织、部署或容量需要独立扩展时才值得支付的成本。
  8. 无法观测和管理的系统，也就无法被可靠地运营。
