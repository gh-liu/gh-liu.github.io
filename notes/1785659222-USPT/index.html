从距离、故障、时间、顺序与复制出发，理解分布式系统的一致性与可用性权衡

https://book.mixu.net/distsys/index.html

  • 是什么（What）：
    • 一本面向工程实践的分布式系统入门书。它从分布式系统的物理约束出发，依次讨论系统模型、CAP 与 FLP、时间与顺序、强一致复制、弱一致复制、Dynamo、CRDT 和 CALM，帮助读者建立分析分布式系统的统一认知模型。
  • 为什么（Why）：
    • 单机上的存储和计算在规模增长后会遇到容量、性能、可用性和地理延迟的上限，只能通过分区与复制扩展到多台机器。但节点之间存在距离、没有共享时钟，并且节点和网络可能独立失败，因此像一台机器一样工作不再是免费的抽象。理解这些约束，才能判断一个系统为何选择一致性、可用性、延迟或容错性中的某种组合。
  • 怎么做（How）：
    • 先明确系统模型、故障模型和一致性契约，再根据业务不变量选择分区、复制与协调策略。必须维持单副本语义的操作，用多数派共识等机制换取安全性；能容忍短暂分歧的操作，可用异步复制、冲突检测、读修复和反熵提高可用性；具备单调性或可交换语义的数据，则优先用 CRDT 等方式减少协调。不要笼统追求强一致或最终一致，而应说明具体保证、故障条件和代价。

核心观点：

分布式系统设计的核心，是在信息传播需要时间和多个组件会独立失败这两条不可消除的事实下，选择合适的抽象与一致性契约。分区和复制提供扩展性、性能与容错能力，也同时引入协调、顺序和分歧问题；系统越想表现得像一台机器，就越需要通信和等待。真正重要的不是找到没有代价的协议，而是识别业务真正需要协调的边界，只为必要的不变量支付一致性成本。

全书可以压缩成一条推导链：

  1. 数据或计算超出单机能力后，需要分区和复制。
  2. 多节点没有共享内存和可靠的全局时钟，消息可能延迟或丢失，节点可能崩溃。
  3. 因而系统天然只有局部知识和偏序，而不是全局真相与全序。
  4. 若要维持单副本语义，节点必须通信、等待并达成共识；网络分区时还必须让部分节点停止服务。
  5. 若业务更看重可用性和低延迟，就要允许副本暂时分歧，并明确检测、合并和收敛规则。
  6. 若数据操作满足交换、结合、幂等，或程序本身具有逻辑单调性，则可以在不建立全序的前提下正确收敛。

1. 分布式系统的目标与代价

分布式编程，是用多台计算机解决原本可以由一台计算机解决的问题，通常是因为问题已经无法经济地装进一台机器。系统仍然只做两类基本工作：存储与计算，但规模会带来三种扩展压力：

  • 规模扩展性（size scalability）：增加节点应提升处理能力，数据增长不应导致延迟失控。
  • 地理扩展性（geographic scalability）：在多个数据中心靠近用户部署，同时合理处理跨地域延迟。
  • 管理扩展性（administrative scalability）：机器数量增加时，运维成本不能同比增长。

扩展性通常要由性能与可用性共同衡量：

  • 性能不只有吞吐量，还包括响应延迟和资源利用率。批处理可以提高吞吐，但会增加单个请求的等待时间。
  • 可用性可写成 uptime / (uptime + downtime)；冗余能让系统容忍局部故障，但组件越多，至少一个组件发生故障的概率也越高。
  • 容错不是系统永不失败，而是先定义预期故障，再保证故障发生后系统仍以明确方式运行。没有进入故障模型的故障，也就没有被协议真正容忍。

两个基本设计手段

手段 主要收益 主要代价
分区（partitioning） 将数据拆成独立子集，扩大容量和并行度，让分区可独立故障 跨分区查询昂贵，热点、数据倾斜和再平衡依赖具体访问模式
复制（replication） 增加读带宽、降低访问距离、提高耐久性和可用性 多份状态必须同步，会产生延迟、分歧、冲突和协调成本

分区解决数据和计算太大的问题，复制解决距离、带宽和单点故障的问题。它们是分布式系统的基本组合拳，但复制既是许多问题的解法，也是许多一致性问题的来源。

2. 系统模型：先说清假设，再讨论正确性

分布式程序具有几个根本特征：

  • 进程在独立节点上并发运行。
  • 节点只快速掌握本地状态，对全局状态的认识可能已经过时。
  • 节点可以独立崩溃和恢复。
  • 网络可能丢失、延迟或重排消息，节点故障与网络故障难以区分。
  • 节点没有天然同步的共享时钟，本地时间戳不能可靠代表全局真实顺序。

系统模型就是对节点能力、通信链路、故障方式、时间与顺序所作的一组假设。假设越弱，算法适用范围越广，但设计越困难；假设越强，推理越简单，却越可能与真实环境不符。

时间模型

模型 假设 工程含义
同步系统 进程同步执行；消息延迟有已知上界；时钟准确 容易推理，但通常不符合真实网络
异步系统 不假设执行速度、消息延迟上界或可用时钟 最保守，不能仅凭等待时间区分故障和延迟
部分同步系统 大部分时间存在可用边界，但偶尔会失效 最接近现实；工程系统通常依赖最终稳定的时段取得进展

现实系统至多是部分同步的。超时不是远端已经失败的证明，只是本地根据历史延迟作出的怀疑。

CAP 与 FLP 的真正含义

FLP 说明：在完全异步系统中，即使网络可靠、最多只有一个进程以崩溃方式失败，也不存在一个确定性共识算法能保证总会终止。算法在不利的消息调度下可能无限期无法决定。因此共识协议无法同时无条件保证安全性与活性，工程实现通常保安全、在极端情况下牺牲活性。

CAP 说明：网络分区已经发生时，强一致性和可用性不能同时保证。

  • CP：保持单副本一致性，让少数派分区停止服务；多数派仍可工作。
  • AP：各分区继续服务，允许状态暂时分歧，分区恢复后再解决冲突。
  • 所谓 CA 设计没有把网络分区纳入可容忍故障；分区出现时只能阻塞，不能理解为现实中可以忽略 P。

CAP 不是平时任意选两个的配置开关。分区不存在时，系统仍需在一致性与延迟之间权衡；分区出现时，才被迫在一致性与可用性之间选择。

一致性是一份契约

一致性不是单一属性，而是系统和程序员之间关于操作结果可预测性的契约：

  • 线性一致性（linearizability）：所有操作看起来原子地发生，并且顺序符合全局真实时间。一个操作完成后，后续操作必须看到它。
  • 顺序一致性（sequential consistency）：所有节点看到同一个操作全序，并保持各节点自身的程序顺序，但该全序不必符合真实时间。
  • 因果一致性（causal consistency）：因果相关的操作按相同顺序可见，并发操作无需强制全序。
  • 以客户端为中心的一致性：围绕会话提供读己之写、单调读等保证，避免用户切换副本后看见状态倒退。
  • 最终一致性（eventual consistency）：停止更新后，副本最终收敛；它没有单独说明多久收敛、收敛到什么值、期间允许哪些异常，因此必须附加更精确的保证。

最终一致本身太弱。工程文档至少还应说明冲突判定方式、合并规则、典型收敛窗口，以及是否可能丢失更新。

3. 时间、顺序与因果关系

单机执行天然产生全序，而分布式系统的自然状态是偏序：每个节点内部有本地顺序，互不通信的事件则可能无法比较。把偏序强制变成全序需要通信、等待，或依赖精确时钟，因此顺序是有成本的资源。

物理时间常被用于三个目的：

  1. 顺序：用时间戳排列事件。
  2. 时长：使用超时推测故障或触发租约。
  3. 解释：把事件映射到人能理解的日期与日志时间。

跨节点物理时钟会漂移，NTP 只能缩小误差，不能创造完美全局时钟。若用最后写入者胜出（LWW），错误时钟可能让旧数据覆盖新数据。物理时间适合展示和有误差边界的工程判断，不应未经论证地当作绝对因果顺序。

逻辑时钟

Lamport 时钟规则：本地事件递增计数；发送消息时携带计数；接收消息后更新为 max(local, received) + 1。若 a → b，则 L(a) < L(b)；但反过来不成立，两个无因果关系的并发事件也可能得到可比较的数字。

向量时钟让每个节点维护一个分量：本地事件递增自己的分量，接收消息时逐项取最大值。由此可以判断两个版本是：

  • 一个明确早于另一个，旧版本可被丢弃；
  • 或二者并发，不应武断覆盖，需要保留并合并。

代价是向量大小随参与者增长，需要裁剪或垃圾回收。逻辑时钟记录的是因果知识，不提供真实时间和持续时长。

故障检测器

故障检测器通常通过心跳和超时输出怀疑，而不是真相：

  • 超时太短，故障发现快，但容易把慢节点误判为故障。
  • 超时太长，误判少，但恢复和选主更慢。
  • 自适应检测器可基于历史延迟输出连续的怀疑程度，由上层按业务风险决定阈值。

故障检测的关键属性是完备性（崩溃节点最终会被怀疑）与准确性（正确节点不被误判）。异步网络中无法永久保证强准确性，只能期待系统稳定后最终准确。

4. 防止分歧：强一致复制

复制协议首先可以按客户端何时收到响应来区分：

方式 写路径 优点 风险
同步复制 等待多个或全部副本确认后响应 耐久性与一致性保证更强 延迟受最慢节点影响，故障时可用性下降
异步复制 本地接受后立即响应，稍后传播 延迟低，对网络抖动不敏感 复制完成前主节点故障可能丢数据，副本会滞后或分歧

进一步看，强一致复制协议是在用更多轮通信购买更强的故障处理能力。

Primary/Backup

  • 所有更新经固定主节点串行化，再把日志复制给备节点。
  • 异步模式存在复制延迟和故障时的数据丢失窗口。
  • 同步确认仍不能单独解决故障切换边界：备节点持久化后、主节点回复客户端前发生故障，客户端会认为失败，但新主节点可能已经提交。
  • 临时网络问题可能导致双主（split brain），因此可靠自动故障切换仍需要共识或外部 fencing 机制。

两阶段提交（2PC）

  1. Prepare/Vote：协调者询问所有参与者是否可以提交；参与者把临时结果写入稳定存储后投票。
  2. Commit/Abort：只有全员同意才提交，否则回滚，再由参与者确认。

2PC 能防止部分参与者提交、部分参与者回滚，却是全票协议：协调者或参与者失联时可能阻塞，必须等待恢复。它解决的是原子提交，不是一个能在分区下自动保持可用的共识协议。

多数派共识：Paxos、Raft、ZAB

分区容错的强一致系统利用多数派交集打破网络分区的对称性：在 2f + 1 个节点中可容忍 f 个节点失效，只允许持有多数票的一侧继续决定，少数派停止写入。

协议通常包含：

  • 角色：稳定期由 leader 协调，followers 复制；角色可以在故障后重选。
  • 任期/epoch：单调增长的逻辑时间，用来识别并拒绝旧 leader 的消息。
  • 多数派：任意两个多数派必有交集，使已被选定的值不能被另一组节点悄悄改写。
  • 持久状态：投票和已接受值必须写入稳定存储，重启后仍要遵守之前承诺。

Paxos 的核心安全要求是：某个值一旦被多数派选定，任何更高编号且再次被选定的提案都必须保持该值。网络不稳定或候选人竞争时，协议可以长期无法取得进展，但不能产生两个已经提交的历史；这正是牺牲活性，保护安全性。

协议 决策方式 主节点 分区容错 主要限制
Primary/Backup 主节点决定 固定 否 可能丢失更新或 split brain，切换多为 best effort
2PC 全体同意 固定协调者 否 单节点或网络故障即可阻塞，尾延迟敏感
Paxos/Raft/ZAB 多数派同意 可重新选举 是 少数派不可用，实现、成员变更和恢复复杂

5. 接受分歧：弱一致复制

放弃单副本语义后，副本可以在分区期间继续接受读写，但系统必须回答三个问题：

  1. 如何发现同一数据的多个并发版本？
  2. 如何合并冲突而不静默丢失业务意图？
  3. 如何让离线或落后的副本最终追上？

Dynamo 的设计组合

Amazon Dynamo 以可用性优先的键值存储展示了一套完整答案：

  • 一致性哈希：把 key 映射到负责节点，降低节点增减时的数据迁移量。
  • 可调部分法定人数：写等待 W-of-N，读联系 R-of-N。增大 W 提高写耐久性，增大 R 提高读到新值的概率。
  • 向量时钟与读修复：识别版本的先后或并发关系；过时版本可丢弃，并发版本交给应用按业务语义合并。
  • Gossip 与 Merkle Tree：后台概率式交换成员与副本信息，并通过分层哈希快速定位差异，执行反熵同步。

R + W > N 只说明固定副本集合中的读写集合会相交，不自动等于强一致性。Dynamo 的 sloppy quorum 会在原节点不可达时让其他节点暂存数据，分区两侧也可继续写，实际参与节点集合可能变化，因此保证仍是概率性的。

不同冲突元数据对应不同语义：

  • 无元数据通常只能选择某个版本，容易静默丢更新。
  • 物理时间戳支持 LWW，但依赖时钟质量，而且最后不等于业务正确。
  • 单一版本号无法表达多条并发历史。
  • 向量时钟能区分因果先后与并发，但元数据更大，应用也必须处理多值。

CRDT：让操作对顺序不敏感

如果系统知道数据类型和操作语义，就不必把值视为无法理解的二进制对象。CRDT 通过满足以下性质的合并操作，让所有看过相同更新的副本最终确定性收敛：

  • 结合律：分组方式不影响结果。
  • 交换律：消息到达顺序不影响结果。
  • 幂等性：重复投递不影响结果。

例如集合并集和 max 满足这些性质，而字符串拼接不满足交换律。计数器、只增集合、PN-Counter、LWW-Register、Multi-Value Register、Observed-Remove Set 等 CRDT 都通过明确的冲突语义换取无协调收敛。

CRDT 不是任何数据自动合并。删除与新增并发时究竟谁获胜、元素能否再次加入，都是业务语义；选错 CRDT 仍会得到确定但错误的结果。

CALM：单调程序无需协调

CALM 将可协调性问题提升到程序层面：逻辑单调的程序可以在无协调条件下最终一致。

  • 单调计算只会随新事实增加结论，既有结论不会被撤回。例如 selection、projection、join、union，以及不带否定的递归 Datalog。
  • 非单调计算可能因新事实推翻旧结论，例如否定、集合差、全称量化和许多聚合。
  • 对全局不存在某记录或总数就是 X作断言，需要确认已经看见全部相关信息，因此需要等待和协调。

这给出比所有操作都强一致更精细的工程原则：让单调部分自由并行和异步传播，只在必须作不可撤回的非单调断言处建立协调边界。

启发点（关键洞察）：

  1. 分布式系统没有免费的单机抽象。隐藏节点、网络和副本差异能降低编程复杂度，却必须用通信、等待和不可用窗口来维护这种幻觉。
  2. CAP 最重要的启示不是背诵 CP/AP，而是网络分区发生后必须明确谁还能写、谁会拒绝服务，以及分歧如何恢复。
  3. 最终一致性不是足够的产品承诺。真正需要评审的是收敛时间、冲突规则、会话保证、更新丢失概率和异常对业务的影响。
  4. 时间戳并不等于因果关系。跨节点排序若影响资金、库存、权限等关键不变量，应使用版本、共识或显式业务规则，而不是盲信机器时钟。
  5. 超时只能产生怀疑，不能证明故障。错误地把慢节点当死节点，是重复执行、双主和脑裂问题的重要来源。
  6. 多数派的价值不只是票更多，而是任意两个多数派必然相交，因此新领导者无法完全绕过已经提交的历史。
  7. 强一致协议主要是在保护安全性：即使暂时不能回答，也不能给出两个互相冲突的已提交答案。可用性优先系统则把冲突处理责任显式交给数据模型和应用。
  8. 能否无协调执行，取决于操作语义而不只取决于基础设施。increment(10) 比 read(); write(x + 10) 保留更多意图，也更容易安全交换和合并。
  9. 数据模型本身就是分布式协议的一部分。选择 LWW、Multi-Value Register 或 OR-Set，本质上是在定义并发冲突时哪些业务事实可以被保留或丢弃。
  10. 最有效的优化往往不是让共识更快，而是缩小必须共识的范围：识别真正的业务不变量，把协调放在断言边界，而不是覆盖整个处理链路。

行动：

  1. 设计分布式功能前写一页 guarantees：列出节点和网络故障模型、一致性级别、允许的陈旧窗口、失败响应语义、重试与去重策略。
  2. 为每条关键业务不变量分类：必须全局同步维护、只需因果顺序、可接受最终收敛，或天然单调；只对第一类引入共识与事务。
  3. 评审超时和故障切换逻辑时，明确区分已失败与被怀疑，检查是否有 fencing token、幂等键或 epoch 防止旧主继续写入。
  4. 使用异步复制或部分 quorum 时，不只配置 N/R/W，还要验证真实节点集合、hinted handoff、读修复、反熵和节点恢复时的行为。
  5. 禁止在关键冲突解决中默认使用 LWW；先回答时钟漂移和并发更新时允许丢掉哪一方，再决定是否适用。
  6. 对购物车、协作编辑、计数和集合类需求，优先检查是否有语义匹配的 CRDT；同时把 add/remove 并发规则写进测试。
  7. 在架构评审里增加一个问题：这个全局顺序真的影响最终正确性吗？若只需要偏序或因果顺序，就不要支付全序成本。
  8. 对共识系统进行故障注入，至少覆盖 leader 回复前崩溃、少数派分区、消息重复与乱序、旧 leader 恢复、成员变更和磁盘状态恢复。
