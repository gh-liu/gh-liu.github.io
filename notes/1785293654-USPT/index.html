S 应用需要等待磁盘、网络和其他设备，但设备延迟远高于 CPU，而且一个服务常常同时管理大量 I/O。

C 如果线程在每个慢操作上阻塞，会消耗大量线程和调度资源；如果持续轮询，又会浪费 CPU。与此同时，“调用立即返回”和“整个操作已经异步完成”经常被混为一谈。

Q 阻塞、非阻塞、I/O 多路复用和异步 I/O 的边界是什么？

A 先把一次 I/O 分成“等待就绪”和“传输数据”两个阶段：阻塞/非阻塞描述调用在等待条件不足时是否睡眠；readiness 模型通知应用何时可以自己传输，completion 模型则由内核执行操作并通知完成。

1. 两阶段模型

以 socket 读取为例：

  1. 等待数据就绪：网卡收包，协议栈把数据放入内核 socket buffer。
  2. 执行读取：把数据从内核缓冲区复制到用户缓冲区。

传统阻塞 I/O 会让调用线程等待两个阶段完成。非阻塞 read 在当前无法读取时立即返回 EAGAIN；数据就绪后，应用仍需再次调用 read 完成传输。

“同步/异步”在不同 API 和文章中定义并不总是一致。讨论具体系统时，直接说清楚谁等待、谁执行数据传输、完成后如何通知，比只贴标签更准确。

2. 三类接口

模型 代表接口 应用看到的语义 常见程序结构
Blocking read() 调用完成后才返回 thread-per-request
Readiness select / poll / epoll 告诉应用“现在操作大概率不会阻塞” event loop
Completion AIO / io_uring 提交操作，完成后取得结果 submission/completion queue

Blocking

当条件不足时，内核把线程置为睡眠；事件发生后线程重新进入可运行队列，等调度器分配 CPU，再从系统调用返回。模型简单，但大量并发阻塞操作通常需要大量线程或其他执行单元。

Non-blocking

文件描述符设为 non-blocking 后，暂时不能完成的操作立即返回。应用可以轮询，但高频轮询会浪费 CPU，因此通常与 readiness 通知组合使用。

普通磁盘文件的语义与 socket 不完全相同；O_NONBLOCK 并不会把所有文件 I/O 自动变成异步操作。

Readiness / I/O multiplexing

select、poll、epoll 等接口允许一个线程等待多个文件描述符的事件。事件表示“现在可以尝试读写”，应用仍要调用 read / write，并且必须正确处理非阻塞语义和边沿/水平触发规则。

多路复用不要求只能使用一个线程。常见设计是一个或多个 event loop 配合 worker pool；线程数由 CPU 工作量、阻塞依赖和延迟目标决定。

Completion

应用提交完整 I/O 请求，内核或运行时执行操作，之后通过 completion queue、回调或事件通知结果。完成通知不仅表示“已经就绪”，还表示请求本身已经执行到完成状态。

io_uring 提供 submission queue 和 completion queue，但它支持的操作及实际执行路径很多，不能简单概括为“所有操作都完全由设备异步完成”。

3. Signal-driven I/O

进程可以请求内核在文件描述符就绪时发送 SIGIO。它属于 readiness 通知：信号告诉应用可以尝试 I/O，读取动作仍由应用执行。由于信号处理和状态管理复杂，服务器程序更常使用 epoll、kqueue 或 completion 接口。

4. 选择模型

  • 并发量小、每个连接逻辑独立：阻塞 I/O + 线程通常最容易实现和调试。
  • 大量 socket、单次处理很短：readiness event loop 可以减少线程数。
  • 存储或网络操作适合批量提交，且平台支持成熟：completion 模型可以减少系统调用和上下文切换。
  • 处理逻辑会长时间占用 CPU：无论何种 I/O 模型，都应避免阻塞 event loop，并考虑 worker pool 和背压。

模型本身不会自动提供正确性。还要处理 partial read/write、取消、超时、连接关闭、背压以及 completion 到达后的对象生命周期。
