读博客：Parse, don’t validate

2026-08-022026-08-02
BLN

不要只检查输入是否合法，而要把检查得到的事实保存在类型中，让非法状态在后续程序里无法表示。

https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/

  • 是什么（What）
    • Parse, don’t validate是一条类型驱动设计原则：不要只检查输入是否满足约束，而要把低结构数据转换为能够表达该约束的、更精确的数据类型
  • 为什么（Why）
    • 普通校验只返回成功或失败，检查得到的事实没有进入类型系统，后续代码仍需重复检查；解析则把事实保存在返回值中，使编译器能够持续维护这个不变量
  • 怎么做（How）
    • 先为业务约束选择精确的数据结构，再把不可靠输入尽早解析为该结构；让解析失败停留在系统边界，让核心逻辑只处理已经满足不变量的数据

核心观点：

校验回答这个值现在是否合法，解析则把答案编码进一个新值，使后续代码不必再问同一个问题。

第二种是加强对参数的要求：

NonEmpty a 在结构上保证至少存在一个元素。现在 head 不需要错误分支，也不需要调用方处理一个理论上不可能发生的结果。与其让函数接收宽泛的数据后不断防御，不如让函数只接收足以兑现其承诺的数据。

校验会丢弃信息，解析会保留信息

下面两个函数做了几乎相同的检查，关键区别只在返回类型：

validateNonEmpty 成功后只返回 ()，也就是没有携带任何新信息。原始值仍然是 [a]，后续函数无法知道它已经通过检查。

parseNonEmpty 则返回 NonEmpty a。它不仅完成了检查，还把列表非空这一事实保存在类型中。此后只要持有这个值，就同时持有了该不变量的证明。

从这个角度看，解析不只是在处理文本。任何把低结构输入转换为高结构输出、并显式表示失败的函数，都可以视为解析器：

解析的价值不只是判断是否合法，而是缩小值的可能性空间。输入类型允许的状态很多，输出类型只允许核心逻辑能够正确处理的状态。

把失败限制在解析阶段

如果校验代码散落在业务处理过程中，就容易形成 LangSec 所说的 shotgun parsing（霰弹式解析）：程序一边处理输入，一边在不同位置补充零散检查，并期待其中某个检查可以捕获所有坏数据。

它会带来两个问题：

  1. 无法从函数签名确认输入是否已经完成全部检查，只能依赖调用约定、注释和测试；
  2. 程序可能先对一部分输入产生副作用，之后才发现另一部分无效，此时必须回滚已经发生的状态变化，而回滚并不总是可行。

解析则倾向于把程序划分为两个阶段：

JSON、命令行参数、数据库记录、URL、HTTP Header 等都位于系统与外部世界的边界。应该尽可能在这些边界完成解析，再让业务逻辑接收领域类型，而不是原始字符串、宽泛对象或带有隐含约束的基础类型。

此时检查不再能够被无意省略，因为后续函数需要它产生的 Map 才能继续运行。

可以归纳为两个动作：

  1. 让非法状态无法表示：使用能够直接表达业务不变量的类型和数据结构，例如 NonEmpty、Map、枚举、和类型（sum type）以及受约束的领域类型；
  2. 把证明责任向调用链上游推，但不要推得过远：尽早转换为最精确的表示，理想位置是系统边界；如果约束只属于某个控制流分支，就在进入该分支时解析，而不是强迫整个系统都携带它。

换句话说：先按照希望拿到的数据编写函数签名，再解决现有输入与它之间的转换问题，而不是让核心逻辑永久迁就最宽泛的输入形式。

具体实践建议

  1. 警惕主要用于报错的 m () 函数：如果一个函数的主要作用是检查并抛错，它很可能应该返回一个更精确的值；
  2. 可以分多轮解析：避免霰弹式解析不等于只能扫描一次。解析器可以先读取判别字段，再根据分支解析其余内容；关键是在输入完整解析前不要执行不可逆的业务动作；
  3. 避免非规范化表示，尤其是可变数据：同一事实存放在多个位置，本身就制造了彼此不一致这种非法状态。确需冗余时，应把同步责任封装在一个小而可信的模块内；
  4. 用抽象数据类型和智能构造器保存难以直接编码的约束：例如整数范围很难仅靠普通代数数据类型表达，可以隐藏构造器，只允许调用会检查范围的函数创建该类型；
  5. 让数据类型指导代码：不要因为当前函数临时需要一个判断，就随手向数据结构中加入 Bool。先确认它是否代表独立状态、互斥分支，或可以由其他字段推导，再选择正确表示。

边界与权衡

Parse, don’t validate是设计方向，不是必须不计成本遵守的教条。

  • 有些不变量在现有语言的类型系统中很难自然表达，强行引入高级类型技术可能让维护成本高于收益；
  • 对简单范围、格式等约束，用私有构造器加智能构造函数通常已经足够，不必追求形式化证明；
  • 解析不一定是程序收到请求后的绝对第一步。为避免拒绝服务攻击，系统有时应该先做低成本鉴权，再解析可能消耗大量资源的输入；
  • 类型保证只覆盖已经编码进类型的不变量，外部依赖故障、并发竞争和运行时资源不足仍需正常处理；
  • 如果暂时无法消除一个不可能分支，至少应把不变量写清楚、缩小影响范围，并用测试保护它。

启发点（关键洞察）：

  1. 检查的结果也应该成为数据：一次检查如果只产生 Bool、() 或异常，就没有给后续代码留下可复用的证据。更好的 API 会返回一个更精确的值；
  2. Maybe 和 Result 不总是更安全的终点：它们能把偏函数变成全函数，但也可能把本可在边界消除的不确定性传播到整个调用链。先判断失败是否真的是该函数领域内的合法可能性；
  3. 类型签名是模块间的不变量协议：返回 NonEmpty a 与返回 [a]，但注释保证非空并不等价。前者会在实现变化破坏承诺时触发编译错误，后者只能依赖人的记忆；
  4. 解析是从可能性更多的世界进入可能性更少的世界：好的领域模型不是保存更多字段，而是准确排除业务不接受的组合；
  5. 失败越靠近边界，核心逻辑越容易推理：当输入错误集中在解析阶段，执行阶段的失败模式就更少，事务、副作用和错误恢复也更容易设计；
  6. 正确的数据结构可以替代大量防御式代码：Map 排除重复键、和类型表达互斥状态、私有构造器保护值域，这些都比散落的条件判断更可靠；
  7. 类型驱动设计是一种迭代过程：不必一开始就知道最终模型。可以先写出核心函数希望接收的类型，再沿调用链向上寻找最合适的解析边界，让编译错误成为重构路线图；
  8. 真正的目标仍然是全函数与可维护的不变量：Parse, don’t validate不是要求把所有规则都塞进类型，而是避免重复、易遗漏、无法被编译器追踪的隐式约定。
